## 1. The data type table (slide 2)

### Q1 (slide 2)

On the AVR (`avr-gcc`) the types are: `char` 8 bits, −128 to +127; `unsigned char` 8 bits, 0 to 255; `int` 16 bits, −32 768 to +32 767; `unsigned int` 16 bits, 0 to 65 535; `long` 32 bits, −2 147 483 648 to +2 147 483 647. A temperature reading goes from −500 to +1200. Which is the smallest type that holds it, and how much of the 2048 bytes of RAM do 300 such readings take?

- A) `int`. 300 readings take 600 bytes, about 29 % of the RAM.
- B) `unsigned int`. 300 readings take 600 bytes, about 29 % of the RAM.
- C) `int`. 300 readings take 300 bytes, about 15 % of the RAM.
- D) `long`. 300 readings take 1200 bytes, about 59 % of the RAM.

> [!success]- Answer
> **A.** `char` stops at +127, and the unsigned types hold no negative values. `int` holds −32 768 to +32 767, so −500 and +1200 fit.
> One `int` is 16 bits = 2 bytes: $300\times2=600$ bytes. $600/2048=0.293$, about 29 %.
> - B: `unsigned int` starts at 0, so −500 does not fit.
> - C: This counts 1 byte per reading. An `int` is 2 bytes.
> - D: `long` holds the range, but it is not the smallest type. It wastes 2 bytes per reading.

## 2. Counting to 255: wrap-around (slide 3)

### Q2 (slide 3)

The slide's loop is `unsigned char z; for(z = 0; z <= 255; z++) PORTB = z;`. `unsigned char` is 8 bits (0 to 255), so the loop never ends. Pass 1 writes 0, pass 2 writes 1. Which value does the 600th pass write to port B?

- A) `0x58`
- B) `0x87`
- C) `0x57`
- D) `0x59`

> [!success]- Answer
> **C.** Pass $k$ writes $(k-1) \bmod 256$, because `z` wraps from 255 to 0.
> $600-1=599$. $599-2\times256=599-512=87$.
> $87=5\times16+7$ = `0x57`.
> - A: This uses $600 \bmod 256=88$ = `0x58`. Pass $k$ writes $k-1$, not $k$.
> - B: 87 is the right value in decimal, but it is written as hex without conversion. Decimal 87 is `0x57`.
> - D: This uses $599 \bmod 255=89$ = `0x59`. A byte has 256 values (0 to 255), so the counter repeats every 256 passes.

## 3. ASCII characters (slide 4)

### Q3 (slide 4)

The slide's program is:

```c
unsigned char myList[] = "012345ABCD";
unsigned char z;
DDRB = 0xFF;                     //PORTB is output
for(z=0; z<10; z++)              //repeat 10 times and increment z
  PORTB = myList[z];             //send the character to PORTB
```

ASCII: `'0'` to `'9'` are `0x30` to `0x39`, `'A'` to `'D'` are `0x41` to `0x44`. The loop test is changed to `z<=10`. What does port B show at the end? And which byte does `PORTB = myList[3] - '0';` send?

- A) Port B ends at `0x44`. `myList[3] - '0'` sends `0x03`.
- B) Port B ends at `0x00`. `myList[3] - '0'` sends `0x03`.
- C) Port B ends at `0x00`. `myList[3] - '0'` sends `0x33`.
- D) Port B ends at `0x44`. `myList[3] - '0'` sends `0x04`.

> [!success]- Answer
> **B.** `z<=10` gives 11 passes, $z=0$ to $z=10$. `myList[10]` is the terminating `0x00` that C adds after the 10 characters. The array has 11 bytes, so this byte is still inside it.
> `myList[3]` is `'3'` = `0x33`. `0x33 - 0x30` = `0x03`, the number 3.
> - A: `0x44` (`'D'`) is the last byte of the old loop `z<10`. The new loop runs one more pass.
> - C: This takes `'0'` as the number 0. The character `'0'` is `0x30`.
> - D: This counts the index from 1, so it takes `'4'` = `0x34`. Index 3 is the fourth character, `'3'`.

## 4. Toggling with bitwise NOT (slide 5)

### Q4 (slide 5)

`PORTB` starts at `0xAA` (`0b10101010`). The line `PORTB = PORTB ^ 0x0F;` runs 201 times. What is the final value of `PORTB`?

- A) `0xAA`
- B) `0x55`
- C) `0x5A`
- D) `0xA5`

> [!success]- Answer
> **D.** XOR with 1 flips a bit, XOR with 0 keeps it. So `^ 0x0F` flips only bits 3 to 0.
> Two XORs give the start value back. 201 is odd, so the result equals one XOR.
> `1010 1010 ^ 0000 1111 = 1010 0101` = `0xA5`.
> - A: This is the result after an even number of XORs. 201 is odd.
> - B: This flips all 8 bits, like `~PORTB` or `^ 0xFF`. The mask `0x0F` flips only the low 4 bits.
> - C: This flips the high 4 bits, as with the mask `0xF0`. `0x0F` is the low half.

## 5. Negative numbers on a port (slide 6)

### Q5 (slide 6)

A signed `char` array (8 bits, two's complement) is sent to port B. The port shows `0xE7` and then `0x9C`. Which two signed values are in the array?

- A) 231 and 156
- B) −24 and −99
- C) −25 and −100
- D) −103 and −28

> [!success]- Answer
> **C.** Both bytes have bit 7 = 1, so both are negative: value = (byte as unsigned) − 256.
> `0xE7` = $14\times16+7=231$, $231-256=-25$. `0x9C` = $9\times16+12=156$, $156-256=-100$.
> Check: $+25$ = `0001 1001`, flip = `1110 0110`, add 1 = `1110 0111` = `0xE7`.
> - A: These are the unsigned readings. The array is signed.
> - B: This flips the bits but forgets to add 1 (`~0xE7` = 24, `~0x9C` = 99).
> - D: This reads bit 7 as a plain minus sign and keeps the other 7 bits (`0x67` = 103, `0x1C` = 28). That is sign-magnitude, not two's complement.

## 6. A big enough counter (slides 7-8)

### Q6 (slide 7)

Exercise 5:

```c
unsigned int z;
for(z=0; z<50000; z++){
  PORTB = 0x55;
  PORTB = 0xAA;
}
```

On the AVR, `int` is 16 bits and signed (−32 768 to +32 767), and `unsigned int` is 16 bits (0 to 65 535). Would plain `int z;` also work? With `unsigned int z;`, how many times is `PORTB` written, and which value does it hold at the end?

- A) No, `int` stops at 32 767. 100 000 writes, and the port ends at `0xAA`.
- B) Yes, because $50\,000\le65\,535$. 100 000 writes, and the port ends at `0xAA`.
- C) No, `int` stops at 32 767. 50 000 writes, and the port ends at `0x55`.
- D) No, `int` stops at 32 767. 100 000 writes, and the port ends at `0x55`.

> [!success]- Answer
> **A.** A signed 16-bit `int` can never reach 50 000, so `z<50000` never becomes false. Counting past 32 767 is signed overflow (undefined behaviour).
> With `unsigned int` the body runs 50 000 times with 2 writes: $50\,000\times2=100\,000$ writes.
> The last write of every pass is `PORTB = 0xAA;`.
> - B: 65 535 is the limit of `unsigned int`. Signed `int` stops at 32 767.
> - C: This counts passes, not writes, and takes the first write of the pass as the last.
> - D: The count is right, but the last line of the body writes `0xAA`, not `0x55`.

### Q7 (slide 8)

For `for(z=0; z<N; z++)` the counter must reach $N$. The unsigned types are `unsigned char` (max 255), `unsigned int` (max 65 535) and `unsigned long` (max 4 294 967 295). Which is the smallest counter type for $N=200$, $N=65\,535$, $N=65\,536$ and $N=4\,000\,000$, in this order?

- A) `unsigned char`, `unsigned long`, `unsigned long`, `unsigned long`
- B) `unsigned char`, `unsigned int`, `unsigned int`, `unsigned long`
- C) `unsigned int`, `unsigned int`, `unsigned long`, `unsigned long`
- D) `unsigned char`, `unsigned int`, `unsigned long`, `unsigned long`

> [!success]- Answer
> **D.** The type's maximum must be at least $N$.
> $200\le255$: `unsigned char`. $65\,535\le65\,535$: `unsigned int`, just enough.
> $65\,536>65\,535$: `unsigned long`. $4\,000\,000\le4\,294\,967\,295$: `unsigned long`.
> - A: This asks for a maximum strictly larger than $N$. The counter only has to reach $N$, so 65 535 fits in `unsigned int`.
> - B: 65 536 is one more than the `unsigned int` maximum. That counter wraps to 0 and the loop never ends.
> - C: This uses the signed `char` limit 127. The counter is unsigned, and `unsigned char` goes to 255.

## 7. Time delays (slides 9-11)

### Q8 (slide 9)

The delay of a loop is $\text{delay}=\dfrac{\text{cycles per pass}\times\text{passes}}{f}$, with $f$ the crystal frequency. A loop takes 6 cycles per pass and runs 20 000 passes. How long is the delay with an 8 MHz crystal, and with the same code on the 16 MHz Uno?

- A) 15 ms at 8 MHz and 30 ms at 16 MHz.
- B) 15 ms at 8 MHz and 7.5 ms at 16 MHz.
- C) 2.5 ms at 8 MHz and 1.25 ms at 16 MHz.
- D) 7.5 ms at 8 MHz and 7.5 ms at 16 MHz.

> [!success]- Answer
> **B.** Total cycles: $6\times20\,000=120\,000$.
> At 8 MHz: $120\,000/8\,000\,000=0.015$ s = 15 ms. At 16 MHz: $120\,000/16\,000\,000=0.0075$ s = 7.5 ms.
> Double the frequency gives half the delay.
> - A: The direction is wrong. A faster clock makes each cycle shorter, so the delay goes down.
> - C: This forgets the 6 cycles per pass: $20\,000/8\,000\,000=2.5$ ms.
> - D: This uses the Uno's cycle time, 62.5 ns, for both crystals: $120\,000\times62.5\text{ ns}=7.5$ ms. At 8 MHz one cycle is 125 ns.

### Q9 (slide 10)

In Exercise 7 the counter is `volatile unsigned int i;` (16 bits, 0 to 65 535). The loop `for(i=0; i<L; i++);` takes 20 cycles per pass at 16 MHz. On the slide, $L=42\,150$ is used for 100 ms. Which loop limit $L$ gives a 25 ms delay, and does it fit the counter?

- A) $L=20\,000$. It fits in `unsigned int`.
- B) $L=400\,000$. It needs `unsigned long`.
- C) $L=20\,000\,000$. It needs `unsigned long`.
- D) $L=10\,538$. It fits in `unsigned int`.

> [!success]- Answer
> **A.** $\text{passes}=\dfrac{\text{delay}\times f}{\text{cycles per pass}}$.
> Cycles: $0.025\times16\,000\,000=400\,000$. Passes: $400\,000/20=20\,000$.
> $20\,000\le65\,535$, so `unsigned int` is big enough.
> - B: 400 000 is the number of cycles. It must still be divided by 20 cycles per pass.
> - C: This puts 25 instead of 0.025 s into the formula: $25\times16\,000\,000/20$.
> - D: This scales the slide's limit: $42\,150/4=10\,537.5$. But 42 150 does not give 100 ms with 20 cycles per pass (it gives 52.7 ms), so it cannot be scaled.

### Q10 (slide 11)

The Uno runs at 16 MHz, but the program says `#define F_CPU 8000000UL`. `_delay_ms()` is turned into a fixed number of clock cycles at compile time. How long does `_delay_ms(10);` really take?

- A) 10 ms. `F_CPU` sets the chip clock to 8 MHz, so the delay is as written.
- B) 20 ms. The cycles are counted for a slower clock, so the wait is twice as long.
- C) 5 ms. The compiler makes 80 000 cycles, and 16 MHz runs them in half the time.
- D) 10 ms. `_delay_ms` measures real time with a timer, so `F_CPU` does not matter.

> [!success]- Answer
> **C.** Cycles from `F_CPU`: $8\,000\,000\times0.010=80\,000$.
> Real clock: $80\,000/16\,000\,000=0.005$ s = 5 ms. The delay is half as long as wanted.
> - A: `F_CPU` does not set the clock. It only tells the compiler what the clock is.
> - B: The direction is wrong. The real clock is faster than `F_CPU`, so the fixed cycles end sooner.
> - D: `_delay_ms` is a busy loop of a fixed cycle count, not a timer. That count comes from `F_CPU`.
