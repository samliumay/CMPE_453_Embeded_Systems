## 1. The toolchain and why C (slides 2-3)

### Q1 (slide 2)

![[cmpe453_lecture_02_1_lecture2_1_p002.jpg]]

The diagram has three arrows: Ideas → C code (editor), C code → machine code (compiler), machine code → AVR (flash programmer). Put the tools `avrdude`, `avr-gcc` and a text editor on the arrows. Which arrow is the only one that needs the board to be connected?

- A) Editor, then `avr-gcc`, then `avrdude`. Only the last arrow, machine code → AVR, needs the board.
- B) Editor, then `avrdude`, then `avr-gcc`. Only the last arrow, machine code → AVR, needs the board.
- C) Editor, then `avr-gcc`, then `avrdude`. The last two arrows need the board, because the compiler must ask the chip its type.
- D) Editor, then `avr-gcc`, then `avrdude`. Only the middle arrow, C code → machine code, needs the board.

> [!success]- Answer
> **A.** The editor writes the C code. `avr-gcc` compiles it (with `avr-objcopy` for the `.hex`). `avrdude` is the flash programmer: it copies the `.hex` into the AVR.
> The editor and the compiler only make files on the laptop. Only the copy into the chip needs the board.
> - B: The two tools are swapped. `avrdude` does not compile. It sends the finished `.hex` to the chip.
> - C: The compiler gets the chip type from the command line (`-mmcu=atmega328p`). "Done compiling" with no board connected is normal.
> - D: Compiling makes a file on the laptop. Nothing reaches the chip in this step.

### Q2 (slide 3)

The compiler produced the instruction `sbi 0x05, 3`. `sbi` means "set bit in I/O register". I/O register 0x05 is `PORTB`, and 0x04 is `DDRB`. What does the instruction do, and which C line gives exactly this instruction?

- A) It makes bit 3 of `PORTB` equal to 1. The C line is `PORTB = 0b00001000;`.
- B) It makes bit 3 of `PORTB` equal to 1. The C line is `PORTB |= 0b00001000;`.
- C) It makes PB3 an output. The C line is `DDRB |= 0b00001000;`.
- D) It writes the value 3 into `PORTB`. The C line is `PORTB |= 0b00000011;`.

> [!success]- Answer
> **B.** `sbi 0x05, 3` sets bit 3 of register 0x05 (`PORTB`) and leaves the other bits alone. `|=` with the mask `0b00001000` does the same. If PB3 is an output, the pin goes to 5 V.
> This shows the slide's reason for C: you write the name `PORTB`, not the number 0x05, and you need not know `sbi`. C is easier to write and to change.
> - A: `=` writes all eight bits, so it also clears bits 0-2 and 4-7. `sbi` changes only one bit.
> - C: The direction register `DDRB` is 0x04. The instruction names 0x05, which is `PORTB`.
> - D: The 3 in `sbi 0x05, 3` is a bit number, not a value. `0b00000011` would set bits 0 and 1.

## 2. Inside a HEX file (slide 4)

### Q3 (slide 4, record)

An Intel HEX record has the form `:LL AAAA TT data CC` (byte count, start address, type, data, checksum, all in hex). A record starts with `:10006000`. At which byte address does its last data byte go, and at which address must the next full record start?

- A) Last byte at 0x0069. Next record at 0x006A.
- B) Last byte at 0x0070. Next record at 0x0071.
- C) Last byte at 0x007F. Next record at 0x0080.
- D) Last byte at 0x006F. Next record at 0x0070.

> [!success]- Answer
> **D.** `10` is 0x10 = 16 bytes, `0060` is the address 0x0060, `00` is the type (data).
> The 16 bytes fill 0x0060 to $\text{0x0060}+16-1=\text{0x0060}+\text{0x0F}=\text{0x006F}$.
> The next record starts at $\text{0x0060}+\text{0x10}=\text{0x0070}$.
> - A: This reads the byte count `10` as decimal ten: $\text{0x0060}+9=\text{0x0069}$. All fields are hex.
> - B: This adds 16 without the $-1$. The first byte is at 0x0060 itself, so 16 bytes end at 0x006F.
> - C: This counts 16 words of 2 bytes, 32 bytes. HEX files count bytes.

### Q4 (slide 4, avr-objdump)

An `avr-objdump -d` listing on the slide has the line `1d0:  ff 92  push r15`. The first number is the byte address in hex. The two bytes are shown in the order they are stored. The AVR is little endian. What is the 16-bit instruction word, and what is its word address?

- A) Word 0xFF92, word address 0x00E8.
- B) Word 0x92FF, word address 0x01D0.
- C) Word 0x92FF, word address 0x00E8.
- D) Word 0x92FF, word address 0x03A0.

> [!success]- Answer
> **C.** Little endian: the first stored byte `ff` is the low byte, the second `92` the high byte. Word = 0x92FF.
> Byte address $\text{0x01D0}=1\cdot256+13\cdot16+0=464$. Word address $=464/2=232=\text{0x00E8}$.
> - A: The word address is right, but the bytes were not swapped. The low byte comes first in memory.
> - B: This keeps the byte address. The CPU counts 16-bit words, so divide by 2.
> - D: This multiplies by 2: $464\cdot2=928=\text{0x03A0}$. A word is 2 bytes, so there are half as many words as bytes.

## 3. Recall: inside the AVR (slide 5)

### Q5 (slide 5)

![[cmpe453_lecture_02_1_lecture2_1_p005.jpg]]

The slide says: data bus 8 bits wide, program bus 16 bits wide. (a) Where is the uploaded Blinker program stored, and on which bus does it reach the CPU? (b) Where does a variable `count` live, and on which bus does it travel? (c) Which of the two is still there after power-off?

- A) (a) Program ROM (flash), over the 8-bit data bus. (b) RAM, over the 16-bit program bus. (c) The program.
- B) (a) Program ROM (flash), over the 16-bit program bus. (b) RAM, over the 8-bit data bus. (c) The program.
- C) (a) Program ROM (flash), over the 16-bit program bus. (b) EEPROM, over the 8-bit data bus. (c) Both.
- D) (a) Program ROM (flash), over the 16-bit program bus. (b) RAM, over the 8-bit data bus. (c) Both, because RAM is on the chip too.

> [!success]- Answer
> **B.** The CPU fetches instructions from the program ROM over the separate program bus, one 16-bit word at a time. Variables are in RAM and move on the 8-bit data bus, the same bus as EEPROM, timers and ports.
> Flash keeps its content without power. RAM loses it. So only the program survives.
> - A: The two buses are swapped. In the diagram the program bus is the thick line from the program ROM to the CPU.
> - C: A normal variable lives in RAM. EEPROM is only for data the program saves on purpose.
> - D: Being on the chip does not matter. RAM is volatile: it loses its content at power-off.

## 4. Compiler, board and library (slides 6-10)

### Q6 (slide 6)

The Arduino "Blink" sketch uses `pinMode(LED_BUILTIN, OUTPUT)`, `digitalWrite(LED_BUILTIN, HIGH)` and `digitalWrite(LED_BUILTIN, LOW)`. `LED_BUILTIN` is D13, and D8-D13 are PB0-PB5. Which three register lines of this course do the same, in this order?

- A) `DDRB |= 0b00100000;`, `PORTB |= 0b00100000;`, `PORTB &= 0b00100000;`
- B) `DDRB |= 0b00010000;`, `PORTB |= 0b00010000;`, `PORTB &= 0b11101111;`
- C) `DDRB |= 0b00100000;`, `PORTB |= 0b00100000;`, `PORTB &= 0b11011111;`
- D) `DDRB |= 0b00100000;`, `PORTB |= 0b00100000;`, `PORTB |= 0b11011111;`

> [!success]- Answer
> **C.** D13 is port B, bit $13-8=5$: PB5. The mask with only bit 5 set is `0b00100000`.
> Output: set bit 5 of `DDRB`. HIGH: set bit 5 of `PORTB`. LOW: AND with a 0 only at bit 5, `0b11011111`, so only PB5 is cleared.
> - A: AND with `0b00100000` keeps bit 5 and clears all other bits. The LED stays on.
> - B: `0b00010000` is bit 4. This counts the fifth digit from the right as bit 5, but the rightmost digit is bit 0.
> - D: OR can only turn bits on. `|= 0b11011111` sets seven bits and never clears PB5.

### Q7 (slides 7-8)

The EasyAVR v7 on slide 7 has its own programmer on the board. The Uno is chosen on slide 8. The ATmega328P has 32768 bytes of flash. How does the machine code get into the Uno's flash, and what does this cost?

- A) A bootloader in the top of the flash receives the `.hex` data over USB and writes it into flash. It takes 512 bytes, so the program can use 32256 bytes.
- B) A programmer chip on the Uno writes the flash directly, like on the EasyAVR. Nothing is used up, so the program can use all 32768 bytes.
- C) A bootloader in the top of the flash receives the `.hex` data over USB and writes it into flash. It takes 512 bytes of SRAM, so 1536 bytes of RAM are left.
- D) A bootloader in the top of the flash receives the `.hex` data over USB and writes it into flash. It takes 1 KB, so the program can use 31744 bytes.

> [!success]- Answer
> **A.** The bootloader sits at 0x7E00-0x7FFF. `avrdude` or the Upload button sends the `.hex` over USB, and the bootloader writes it into flash.
> Cost: $32768-512=32256$ bytes for the program. This is the "Maximum is 32256 bytes" the IDE prints.
> - B: The Uno has no separate programmer for the ATmega328P. The IDE's maximum of 32256 bytes shows that part of the flash is taken.
> - C: The bootloader is stored in flash, not in SRAM. The IDE still reports 2048 bytes of RAM.
> - D: 1 KB is the size of the EEPROM. The bootloader takes 512 bytes: $32768-1024=31744$ is the wrong subtraction.

## 5. Blinker: circuit and pin mapping (slides 11-13)

### Q9 (slide 12)

The pin gives 5 V. The circuit is rebuilt with a 220 Ω resistor and a green LED that drops about 2.0 V. The pinout diagram of slide 13 says "recommended 20 mA" per pin and 40 mA absolute maximum. What is the current, and is it inside the recommended value?

- A) About 22.7 mA. It is above the recommended 20 mA but below the 40 mA maximum.
- B) About 9.1 mA. It is inside the recommended value.
- C) About 13.6 mA. It is inside the recommended value.
- D) About 31.8 mA. It is above the recommended 20 mA but below the 40 mA maximum.

> [!success]- Answer
> **C.** Voltage across the resistor: $5-2.0=3.0$ V. Ohm's law: $I=3.0/220=0.0136$ A $\approx13.6$ mA.
> $13.6<20$, so it is inside the recommended value.
> - A: This forgets the LED drop: $5/220=22.7$ mA.
> - B: This uses the LED voltage instead of the resistor voltage: $2.0/220=9.1$ mA.

### Q10 (slide 13)

The pin map is D0-D7 = PD0-PD7, D8-D13 = PB0-PB5, A0-A5 = PC0-PC5. LEDs are on Arduino D4 and D6, and one more on A5. Give the AVR pin names, and one line that makes D4 and D6 outputs and keeps the other pins of that port as they are.

- A) PD4, PD6 and PC5. `DDRD = 0b01010000;`
- B) PD4, PD6 and PC5. `DDRD |= 0b00001010;`
- C) PD4, PD6 and PA5. `DDRD |= 0b01010000;`
- D) PD4, PD6 and PC5. `DDRD |= 0b01010000;`

> [!success]- Answer
> **D.** D4 and D6 are in D0-D7: port D with the same bit number, PD4 and PD6. A5 is PC5.
> The mask with bits 6 and 4 set is `0b01010000`. `|=` on `DDRD` sets these two bits and keeps the other six.

## 6. Blinker: the code and `|=` (slides 14-18)

### Q11 (slide 15)

The empty sketch has `setup()` (runs once) and `loop()` (runs again and again). The course deletes both and writes `main()`:

```c
#include <avr/io.h>
#include <util/delay.h>
int main(void) {
  DDRB |= 0b00000001;
  while (1) {
    PORTB = 0b00000001;
    _delay_ms(1000);
    PORTB = 0b00000000;
    _delay_ms(1000);
  }
  return 0;
}
```

Which lines do the job of `setup()`, and which do the job of `loop()`?

- A) `setup()`: the two `#include` lines. `loop()`: everything inside `main()`.
- B) `setup()`: `DDRB |= 0b00000001;`. `loop()`: the two `PORTB = ...` lines and the two `_delay_ms(1000);` lines.
- C) `setup()`: `DDRB |= 0b00000001;` and `PORTB = 0b00000001;`. `loop()`: the other three lines inside `while (1)`.
- D) `setup()`: `DDRB |= 0b00000001;`. `loop()`: the body of `while (1)` and `return 0;`.

> [!success]- Answer
> **B.** The part before `while (1)` runs once, like `setup()`. Here it is only `DDRB |= 0b00000001;`.
> The body of `while (1)` repeats forever, like `loop()`: the two `PORTB = ...` lines and the two delays.
> - A: `#include` runs nothing. It only gives names to the compiler.
> - C: `PORTB = 0b00000001;` is inside `while (1)`, so it runs in every period. The LED must turn on again each time.
> - D: `while (1)` never ends, so `return 0;` is never reached.

### Q13 (slides 17-18, change the blink)

Change the Blinker so that the on-board LED (D13 = PB5) is on for 200 ms and off for 800 ms. Which mask do the `DDRB` and `PORTB` lines use, and what is the blink frequency?

- A) Mask `0b00001101`, delays 200 ms then 800 ms, frequency 1 Hz.
- B) Mask `0b00010000`, delays 200 ms then 800 ms, frequency 1 Hz.
- C) Mask `0b00100000`, delays 200 ms then 800 ms, frequency 5 Hz.
- D) Mask `0b00100000`, delays 200 ms then 800 ms, frequency 1 Hz.

> [!success]- Answer
> **D.** PB5 is bit 5, so the mask is `0b00100000`: `DDRB |= 0b00100000;`, then `PORTB = 0b00100000;` with `_delay_ms(200);`, then `PORTB = 0b00000000;` with `_delay_ms(800);`.

> - B: `0b00010000` is bit 4. This counts the fifth digit from the right as bit 5.
> - C: This uses only the on-time: $1/0.2\text{ s}=5$ Hz. The period is on-time plus off-time.

### Q14 (slides 17-18, find the bug)

A student rewrites the loop with the OR-assign operator in both lines "to be safe". The LED turns on and never turns off. Why, and what is the fix that turns off only PB0?

```c
while (1) {
  PORTB |= 0b00000001;
  _delay_ms(1000);
  PORTB |= 0b00000000;
  _delay_ms(1000);
}
```

- A) `|=` compares `PORTB` with 0, like `==`, so nothing is stored. Fix: `PORTB = 0;`.
- B) `|= 0b00000000` sets all bits of `PORTB` to 1. Fix: `PORTB = 0b00000000;`.
- C) OR with 0 keeps every bit, so bit 0 stays 1. Fix: `PORTB &= 0b11111110;`.
- D) OR with 0 keeps every bit, so bit 0 stays 1. Fix: `PORTB &= 0b00000001;`.

> [!success]- Answer
> **C.** `PORTB |= 0b00000000;` is `PORTB = PORTB | 0b00000000;`. Since $x\,\mid\,0=x$, no bit changes and PB0 stays 1.
> `|=` can only turn bits on. AND with a 0 only at bit 0 clears PB0 and keeps the rest.
> - A: `|=` is an assignment, not a comparison. It stores `PORTB | 0b00000000`, which is the old value.
> - B: OR with 0 changes nothing. Also `PORTB = 0b00000000;` turns off all of port B, not only PB0.
> - D: AND with `0b00000001` keeps bit 0 and clears the others. PB0 stays on.

### Q19 (slide 26)

The Blinker keeps the LED on for `_delay_ms(1000)` and off for `_delay_ms(1000)`. (a) How many times does it turn on in one minute? (b) `_delay_ms` is a counting loop sized from `F_CPU`. Suppose the code is compiled with `F_CPU` = 8000000 but the board still runs at 16 MHz. What do you see?

- A) (a) 60 times. (b) It blinks twice as fast, at 1 Hz.
- B) (a) 30 times. (b) It blinks half as fast, at 0.25 Hz.
- C) (a) 30 times. (b) No change, because `_delay_ms` counts milliseconds, not clock cycles.
- D) (a) 30 times. (b) It blinks twice as fast, at 1 Hz.

> [!success]- Answer
> **D.** (a) One period is $1+1=2$ s. In 60 s: $60/2=30$ times.
> (b) For 8 MHz the compiler counts 8 000 000 cycles for 1000 ms. The real clock gives 16 000 000 cycles per second, so the delay lasts $8\,000\,000/16\,000\,000=0.5$ s. On 0.5 s, off 0.5 s: period 1 s, 1 Hz.
> - A: This takes 1 s as the period. The period is on-time plus off-time, 2 s.
> - B: This turns the ratio the wrong way: $16/8=2$ s per delay, period 4 s, 0.25 Hz. A faster clock finishes the count sooner.
> - C: The chip has no millisecond timer here. The loop counts cycles, and the count is computed from `F_CPU`.
