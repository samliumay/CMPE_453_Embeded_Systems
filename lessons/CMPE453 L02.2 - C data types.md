# CMPE 453 · Lecture 2.2 · C data types for the AVR

> [!summary] In short
> - On the AVR: `char` 8, `int` 16, `long` 32, `float` and `double` 32 bits. $n$ bits hold $0\ldots2^n-1$ (unsigned) or $-2^{n-1}\ldots2^{n-1}-1$ (signed).
> - Use the smallest type that fits. `unsigned char` = `uint8_t` = one port.
> - Unsigned arithmetic wraps modulo $2^n$: $255+1\to0$. A loop test the counter can never fail loops forever.
> - A character is its ASCII byte: `'0'` = `0x30`, `'A'` = `0x41`. A negative number $-m$ is the byte $256-m$ (two's complement).
> - Delays: `for` loop (compiler and crystal dependent), `_delay_ms()` (needs `F_CPU`, `-Os`, a constant argument), or timers.

## 1. The data type table (slide 2)
![[cmpe453_lecture_02_2_lecture2_2_p002.jpg]]

**Notes.** A byte is 8 bits, bit 7 (left) to bit 0 (right). Bit $n$ is worth $2^n$. `0xAA` = `0b10101010` = $128+32+8+2=170$.

| Data type | Size | Range | `<stdint.h>` name |
|---|---|---|---|
| `unsigned char` | 8 bits | 0 to 255 | `uint8_t` |
| `char` | 8 bits | −128 to +127 | `int8_t` (as `signed char`) |
| `unsigned int` | 16 bits | 0 to 65 535 | `uint16_t` |
| `int` | 16 bits | −32 768 to +32 767 | `int16_t` |
| `unsigned long` | 32 bits | 0 to 4 294 967 295 | `uint32_t` |
| `long` | 32 bits | −2 147 483 648 to +2 147 483 647 | `int32_t` |
| `float`, `double` | 32 bits | ±1.175e−38 to ±3.402e38 | |

Use `unsigned char` whenever the value fits in 0 to 255: a port is 8 bits, the ALU adds 8 bits in one step, and the chip has only 2048 bytes of RAM. Example: 500 readings of 0 to 200 take 500 bytes as `unsigned char` (24 % of RAM) and 1000 bytes as `int` (49 %).

> [!warning] Watch out
> - Slide error: the table says `long` goes up to +2 147 483 648. Correct is +2 147 483 647 ($=2^{31}-1$).
> - On a PC `int` is 32 bits and `double` 64 bits. On the AVR `int` is 16 bits and `double` 32 bits (default `avr-gcc`).
> - Plain `char` is signed in `avr-gcc`, but a compiler option can flip it. When the sign matters write `signed char` or `unsigned char`.

> [!question]- Check (slide 2): A temperature reading goes from −500 to +1200. Which is the smallest type of the table that holds it? How much of the 2048 bytes of RAM do 300 such readings take?
> `char` is too small: its range is −128 to +127. `unsigned char` and `unsigned int` cannot hold negative values.
> `int` (16 bits) holds −32 768 to +32 767, and both −500 and +1200 are inside. So **`int`** (`int16_t`).
> One `int` is 16 bits = 2 bytes. $300\times2=600$ bytes.
> $600/2048=0.293$, so about **29 %** of the RAM.

## 2. Counting to 255: wrap-around (slide 3)
![[cmpe453_lecture_02_2_lecture2_2_p003.jpg]]

**Notes.** Exercise 1 sends 00 to FF to port B.

```c
#include <avr/io.h>          //standard AVR header
int main(void)
{
  unsigned char z;
  DDRB = 0xFF;               //PORTB is output
  for(z = 0; z <= 255; z++)
    PORTB = z;
  return 0;
}
```

`DDRB = 0xFF` makes all 8 pins outputs. `PORTB` then counts in binary: `0x00`, `0x01`, ..., `0xFF`.

**Wrap-around.** $255+1=256$ needs a ninth bit. The byte has none, so the variable becomes 0. Unsigned arithmetic on $n$ bits is done modulo $2^n$:
- `unsigned char`: $255+1\to0$, $0-1\to255$, $250+10=260\to4$.
- `unsigned int` (16 bits): $65\,535+1\to0$.

The loop **never ends**: `z <= 255` is false only when $z\ge256$, and an `unsigned char` can never hold 256.

Two fixes to send `0x00` to `0xFF` exactly once: use `unsigned int z;`, or stop on the wrap:

```c
unsigned char z = 0;
do {
  PORTB = z;                 // 0x00, 0x01, ..., 0xFF
  z++;                       // after 0xFF, z wraps to 0x00
} while (z != 0);            // ... and the loop stops
```

> [!warning] Watch out
> - `-Wall` gives no warning for `z <= 255`. `-Wextra` says "comparison is always true due to limited range of data type". Compile with `-Wall -Wextra`.
> - `z < 255` does end: it sends `0x00` to `0xFE`, 255 values.
> - The wrap rule is for unsigned types only. Signed overflow is undefined behaviour.

> [!question]- Check (slide 3): The slide's loop `for(z = 0; z <= 255; z++) PORTB = z;` never ends. Which value does the 600th pass write to port B?
> Pass 1 writes 0, pass 2 writes 1, so pass $k$ writes $(k-1) \bmod 256$, because `z` wraps from 255 to 0.
> $k=600$: $600-1=599$.
> $599-2\times256=599-512=87$.
> $87=5\times16+7$, so port B shows **`0x57`**. The counter has wrapped two times before this pass.

## 3. ASCII characters (slide 4)
![[cmpe453_lecture_02_2_lecture2_2_p004.jpg]]

**Notes.** ASCII gives each character a number. Digits `'0'` to `'9'` are `0x30` to `0x39`. Capitals `'A'` to `'Z'` are `0x41` to `0x5A`. A string is an array of bytes.

```c
unsigned char myList[] = "012345ABCD";
unsigned char z;
DDRB = 0xFF;                     //PORTB is output
for(z=0; z<10; z++)              //repeat 10 times and increment z
  PORTB = myList[z];             //send the character to PORTB
```

Port B shows `30 31 32 33 34 35 41 42 43 44`.

The digit $d$ has code `0x30` + $d$, so `c - '0'` turns a digit character back into its value.

> [!warning] Watch out
> - `0` is the number zero (`0x00`). `'0'` is one character (`0x30`). `"0"` is a string of two bytes (`0x30 0x00`).
> - `"012345ABCD"` has 10 visible characters but the array has 11 bytes: C adds a terminating `0x00`.

> [!question]- Check (slide 4): In the slide's program the loop test is changed to `z<=10`. What does port B show at the end? And which byte does `PORTB = myList[3] - '0';` send?
> `z<=10` gives 11 passes, $z=0$ to $z=10$. The last pass sends `myList[10]`. That is the terminating byte C adds after the 10 characters, so port B ends at **`0x00`** (all LEDs off). It is still inside the array, because the array has 11 bytes.
> `myList[3]` is the character `'3'` = `0x33`. `'0'` = `0x30`. $\mathtt{0x33}-\mathtt{0x30}=$ **`0x03`**: the number 3, not the character.

## 4. Toggling with bitwise NOT (slide 5)
![[cmpe453_lecture_02_2_lecture2_2_p005.jpg]]

**Notes.** To toggle a port is to flip all its bits: `PORTB = ~PORTB;`.

```c
DDRB = 0xFF;                   //PORTB is output
PORTB = 0xAA;                  //PORTB is 10101010
unsigned char z;
for(z=0; z < 200; z++)         //run the next line 200 times
  PORTB = ~ PORTB;             //toggle PORTB
while(1);                      //stay here forever
```

`0xAA` = `0b10101010` flips to `0x55` = `0b01010101`, then back. Toggling twice changes nothing. After an **even** number of toggles the port is back at the start value, after an **odd** number it holds the inverse. 200 is even, so port B ends at `0xAA`. `unsigned char z` is fine because $200\le255$.

| C | Read as | Example |
|---|---|---|
| `~a` | NOT | `~0xAA = 0x55` |
| `a & b` | AND | `0xAA & 0x0F = 0x0A` |
| `a \| b` | OR | `0xAA \| 0x0F = 0xAF` |
| `a ^ b` | XOR | `0xAA ^ 0xFF = 0x55` |
| `a << n` | shift left | `1 << 6 = 0x40` |
| `a >> n` | shift right | `0x80 >> 3 = 0x10` |

> [!warning] Watch out
> `~` flips 8 bits. `!` (logical NOT) gives only 0 or 1: `!0xAA` is `0`.

> [!question]- Check (slide 5): `PORTB` starts at `0xAA` as on the slide. The loop line is replaced by `PORTB = PORTB ^ 0x0F;` and the loop runs 201 times. What is the final value of `PORTB`?
> XOR with 1 flips a bit, XOR with 0 keeps it. So `^ 0x0F` flips only bits 3 to 0. Bits 7 to 4 never change.
> Doing it twice gives the start value back. 201 is odd, so the result is the same as one XOR.
> `1010 1010 ^ 0000 1111 = 1010 0101` = **`0xA5`**.
> (`~PORTB` is the same as `PORTB ^ 0xFF`: it flips all 8 bits.)

## 5. Negative numbers on a port (slide 6)
![[cmpe453_lecture_02_2_lecture2_2_p006.jpg]]

**Notes.** A signed `char` stores $-m$ in two's complement: the byte $256-m$. Bit 7 is the sign bit.

Recipe: write $+m$ in binary, flip every bit, add 1. Example $-4$: `0000 0100` → `1111 1011` → `1111 1100` = `0xFC` ($256-4=252$). Reading back: if bit 7 is 1, the value is (byte as unsigned) − 256.

| Value | Hex | Value | Hex |
|---|---|---|---|
| −128 | `80` | 0 | `00` |
| −4 | `FC` | +1 | `01` |
| −1 | `FF` | +127 | `7F` |

```c
char mynum[] = {-4,-3,-2,-1,0,+1,+2,+3,+4};
unsigned char z;
DDRB = 0xFF;                      //PORTB is output
for(z=0; z<=8; z++)
  PORTB = mynum[z];
```

Port B shows `FC FD FE FF 00 01 02 03 04`. The array has 9 elements, so the loop runs `z<=8`.

> [!warning] Watch out
> The LEDs cannot tell `0xFC` as `unsigned char` (252) from `0xFC` as `signed char` (−4). Only the type in the program decides.

> [!question]- Check (slide 6): A `char` array is sent to port B as on the slide. The port shows `0xE7` and then `0x9C`. Which two signed values are in the array? Check the first one with the flip-and-add-1 recipe.
> `0xE7` = `1110 0111`: bit 7 is 1, so the value is negative. Unsigned: $14\times16+7=231$. Signed: $231-256=$ **−25**.
> `0x9C` = `1001 1100`: bit 7 is 1. Unsigned: $9\times16+12=156$. Signed: $156-256=$ **−100**.
> Check of −25: $+25$ = `0001 1001`. Flip every bit: `1110 0110`. Add 1: `1110 0111` = `0xE7`. It matches.

## 6. A big enough counter (slides 7-8)
![[cmpe453_lecture_02_2_lecture2_2_p007.jpg]]
![[cmpe453_lecture_02_2_lecture2_2_p008.jpg]]

**Notes.** Exercise 5 toggles 50 000 times with `unsigned int z;`. Exercise 6 toggles 100 000 times with `unsigned long z;`. The body of both:

```c
for(z=0; z<100000; z++){
  PORTB = 0x55;
  PORTB = 0xAA;
}
```

For `z < N` the counter must **reach** $N$ for the test to fail. Pick the smallest unsigned type whose maximum is at least $N$:

| Largest value | Type |
|---|---|
| up to 255 | `unsigned char` |
| up to 65 535 | `unsigned int` |
| up to 4 294 967 295 | `unsigned long` |

$100\,000>65\,535$, so a 16-bit counter wraps before reaching it and the loop never ends. That is the slide's "important" mark.

> [!warning] Watch out
> - Each pass writes the port twice. The counter counts passes, not port changes.
> - `for(i=0; i<256; i++)` needs `unsigned int`: the counter must hold 256.
> - Slide typo: the comment "toggle PB 100,00 times" means 100 000.

> [!question]- Check (slide 7): Exercise 5 uses `unsigned int z;` and `z<50000`. Would plain `int z;` also work on the AVR? How many times is `PORTB` written in total, and which value does it hold at the end?
> No. On the AVR `int` is 16 bits and signed, so its largest value is 32 767. The counter can never reach 50 000, so `z<50000` never becomes false. Counting past 32 767 is signed overflow, which is undefined behaviour. `unsigned int` goes up to 65 535, and $50\,000\le65\,535$.
> The body runs 50 000 times and writes the port twice per pass: $50\,000\times2=$ **100 000 writes**.
> The last write of every pass is `PORTB = 0xAA;`, so the port ends at **`0xAA`**.

> [!question]- Check (slide 8): Give the smallest unsigned counter type for the loop `for(z=0; z<N; z++)` with $N=200$, $N=65\,535$, $N=65\,536$ and $N=4\,000\,000$.
> The counter must reach $N$, so the type's maximum must be at least $N$.
> - $N=200$: $200\le255$, so `unsigned char`.
> - $N=65\,535$: $65\,535\le65\,535$, so `unsigned int` is just enough.
> - $N=65\,536$: $65\,536>65\,535$, so `unsigned long`. One more pass costs two more bytes for the counter.
> - $N=4\,000\,000$: $65\,535<4\,000\,000\le4\,294\,967\,295$, so `unsigned long`.

## 7. Time delays (slides 9-11)
![[cmpe453_lecture_02_2_lecture2_2_p009.jpg]]
![[cmpe453_lecture_02_2_lecture2_2_p010.jpg]]
![[cmpe453_lecture_02_2_lecture2_2_p011.jpg]]

**Notes.** Three ways to wait: (1) a simple `for` loop, (2) predefined functions (`_delay_ms()`, `_delay_us()` in avr-libc, `delay_ms()` in CodeVision), (3) AVR timers (later).

$$\text{delay}=\frac{\text{cycles per pass}\times\text{number of passes}}{f}$$

On the Uno $f=16$ MHz, one cycle is 62.5 ns. Cycles per pass depend on the compiler, so a `for`-loop delay is not portable.

Exercise 7 (slide 10) uses `for(i=0; i<42150; i++);` inside `delay100ms()`.

> [!warning] The empty loop disappears
> With `-Os` (also used by the Arduino IDE) `avr-gcc` deletes the empty loop: `delay100ms` compiles to a single `ret`. Fix 1: `volatile unsigned int i;` (the loop stays, but our estimate is 52.7 ms, not 100 ms). Fix 2, better: `_delay_ms(100);`.

Rules for `_delay_ms()`: `#include <util/delay.h>`, `F_CPU` defined before the include (or `-DF_CPU=16000000UL`), a compile-time constant argument, optimisation on. Then it is exact: `_delay_ms(10)` is 160 000 cycles at 16 MHz.

Exercise 8, clean version:

```c
#define F_CPU 16000000UL       // 16 MHz clock
#include <avr/io.h>
#include <util/delay.h>
int main(void)
{
  DDRB = 0xFF;                 // PORTB is output
  while (1) {
    PORTB = 0x55;              // 0101 0101
    _delay_ms(10);             // wait 10 milliseconds
    PORTB = 0xAA;              // 1010 1010: every bit flipped
    _delay_ms(10);
  }
  return 0;
}
```

> [!warning] Errors on slide 11 (Exercise 8)
> - Comment "delay in d microseconds": correct is **milliseconds**.
> - Comment "PORTA is output": correct is **PORTB**. The ATmega328P has no port A.
> - `delay_ms` is defined inside `main` (a nested function, not standard C) and passes a variable to `_delay_ms`.
> - `0xFF` and `0x55` differ only in bits 7, 5, 3, 1, so this does not toggle all bits. Use `0x55`/`0xAA`.

> [!info] The symbols in the delay formula (beyond the slides)
> - XTAL1 and XTAL2 (slide 9) are the two pins of the chip where the crystal is connected. The crystal sets the clock frequency $f$.
> - One clock cycle lasts $1/f$. At 16 MHz: $1/16\,000\,000\text{ s}=62.5$ ns. Most AVR instructions take 1 or 2 cycles.
> - A "pass" is one run of the loop: test the counter, add 1, jump back. "Cycles per pass" is the sum of the cycles of these instructions. The compiler chooses the instructions, so this number changes with the compiler and its options.
> - So a loop delay depends on two things the C source does not show: the crystal ($f$) and the compiler (cycles per pass).

> [!info] Where the 52.7 ms comes from (beyond the slides)
> With `volatile unsigned int i;` our `avr-gcc` makes a loop of 11 instructions that take 20 cycles per pass. Then, with the formula above:
> $$\text{delay}=\frac{20\times42\,150}{16\,000\,000}=\frac{843\,000}{16\,000\,000}=0.0527\text{ s}=52.7\text{ ms}$$
> For 100 ms the loop would need $0.1\times16\,000\,000/20=80\,000$ passes. That is more than 65 535, so `unsigned int` is too small. A `long` counter changes the cycles per pass again. This is why the slide says "try different numbers on your compiler".

> [!question]- Check (slide 9): A delay loop takes 6 cycles per pass and runs 20 000 passes. How long is the delay with an 8 MHz crystal? And with the same code on the 16 MHz Uno?
> $\text{delay}=\dfrac{\text{cycles per pass}\times\text{passes}}{f}$
> Total cycles: $6\times20\,000=120\,000$.
> At 8 MHz: $120\,000/8\,000\,000=0.015$ s = **15 ms**.
> At 16 MHz: $120\,000/16\,000\,000=0.0075$ s = **7.5 ms**.
> Double the crystal frequency gives half the delay. That is the slide's "a function of crystal frequency".

> [!question]- Check (slide 10): In Exercise 7 the counter is made `volatile unsigned int i;` and the loop takes 20 cycles per pass at 16 MHz. Which loop limit gives a 25 ms delay? Does it fit the counter?
> Solve the delay formula for the passes: $\text{passes}=\dfrac{\text{delay}\times f}{\text{cycles per pass}}$.
> Cycles needed: $0.025\times16\,000\,000=400\,000$.
> Passes: $400\,000/20=$ **20 000**, so `for(i=0; i<20000; i++);`.
> $20\,000\le65\,535$, so `unsigned int` is big enough.
> On another compiler or with other options the 20 changes, and the limit must be found again.

> [!question]- Check (slide 11): The Uno runs at 16 MHz, but the program says `#define F_CPU 8000000UL`. How long does `_delay_ms(10);` really take?
> `_delay_ms` is turned into a fixed number of clock cycles at compile time, computed from `F_CPU`.
> Cycles the compiler makes: $8\,000\,000\times0.010=80\,000$.
> The real clock is 16 MHz: $80\,000/16\,000\,000=0.005$ s = **5 ms**.
> The delay is half as long as wanted. `F_CPU` does not set the clock, it only tells the compiler what the clock is.

## Key formulas and terms
| Term | Meaning / formula |
|---|---|
| Ranges | unsigned $n$ bits: $0\ldots2^n-1$. Signed: $-2^{n-1}\ldots2^{n-1}-1$ |
| AVR sizes | `char` 8, `int` 16, `long` 32, `float`/`double` 32 bits |
| Wrap-around | unsigned arithmetic is modulo $2^n$: $255+1\to0$, $0-1\to255$ |
| ASCII | `'0'` = `0x30` ... `'9'` = `0x39`, `'A'` = `0x41` |
| Toggle | `PORTB = ~PORTB;` even count returns to the start value |
| Two's complement | $-m\to256-m$: −1 = `FF`, −4 = `FC`, −128 = `80` |
| Counter type | smallest type whose maximum ≥ loop limit |
| Loop delay | cycles per pass × passes / $f$ |
| `_delay_ms` | needs `F_CPU`, `-Os`, a constant argument |

## Check yourself
> [!question]- 1. `unsigned char x = 200; x = x + 100;` What is `x`? And `unsigned int y = 65535; y++;` on the AVR?
> $300-256=44=$ **`0x2C`**. `y` is 16 bits on the AVR: $65\,536-65\,536=$ **0**. (On a PC `y` would be 65 536.)

> [!question]- 2. Find the bug: `unsigned char i; for (i = 0; i < 300; i++) PORTB = i;`
> `i` is at most 255, so `i < 300` is always true and the loop never ends. Fix: `unsigned int i;`. Then `PORTB = i` keeps the low byte, so 256 to 299 appear as `0x00` to `0x2B`.

> [!question]- 3. Which bytes does port B show for the string "CMPE453"? How many bytes does the array occupy?
> `43 4D 50 45 34 35 33`. 7 characters plus the terminating `0x00` = **8 bytes**.

> [!question]- 4. `PORTB` starts at `0x0F` and `PORTB = ~PORTB;` runs 75 times. Final value?
> 75 is odd, so the result is `~0x0F` = **`0xF0`**.

> [!question]- 5. `signed char a[] = {-1, -128, 127, -16};` is sent to port B. Which hex values appear?
> $256-1=255$, $256-128=128$, 127, $256-16=240$: **`FF 80 7F F0`**.

> [!question]- 6. A student writes `for(i=0;i<42150;i++);` as a delay with `-Os`. The LEDs never seem to blink. Why? Two fixes.
> The loop body is empty, so the optimiser deletes it. No delay, the LEDs look half-bright. Fix 1: `volatile unsigned int i;`. Fix 2: `#define F_CPU 16000000UL`, `#include <util/delay.h>`, `_delay_ms(100);`.
