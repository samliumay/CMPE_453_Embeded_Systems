## 1. Four steps to use the UART (slide 2)

### Q1 (slide 2)

The four steps are: I set the baud rate, II enable the transmitter and/or receiver, III to send wait for `UDRE0` = 1 and write `UDR0`, IV to receive wait for `RXC0` = 1 and read `UDR0`. A program only sends text and never receives. Which steps does it need, and how often does each one run?

- A) Steps I to IV. Steps I and II run once at the start, steps III and IV run for every byte.
- B) Steps I, II and III. Steps I and II run once at the start, step III runs for every byte.
- C) Steps I to IV. All four steps run again for every byte that the program sends.
- D) Steps I, II and III. All three steps run again for every byte that the program sends.

> [!success]- Answer
> **B.** A send-only program never reads `UDR0`, so step IV is not needed. In step II only `TXEN0` is set.
> Baud rate and enable bits keep their values, so steps I and II run once.
> Step III runs for every byte: wait for `UDRE0` = 1, then write the byte to `UDR0`.
> - A: Step IV belongs to receiving. A program that never receives does not need it.
> - C: Step IV is not needed, and the set-up steps do not have to be repeated: the registers keep their values.
> - D: The right steps, but steps I and II are set-up. Repeating them for every byte only wastes time.

## 2. Setting the baud rate: UBRR0 (slides 3-5)

### Q2 (slide 3)

An Uno ($f_{osc}$ = 16 MHz) is set up for 9600 baud in normal mode with `UBRR0` = 103. By mistake the program also sets `U2X0` = 1. Normal mode: $\text{BAUD}=f_{osc}/(16(\text{UBRR0}+1))$. Double speed (`U2X0` = 1): $\text{BAUD}=f_{osc}/(8(\text{UBRR0}+1))$. Which baud rate does the Uno really use?

- A) 4807.7 baud
- B) 9615.4 baud
- C) 19 417.5 baud
- D) 19 230.8 baud

> [!success]- Answer
> **D.** With `U2X0` = 1 the divider is 8, not 16:
> $$\text{BAUD}=\frac{16\,000\,000}{8\cdot(103+1)}=\frac{16\,000\,000}{832}=19\,230.8$$
> That is twice the wanted rate. The terminal at 9600 baud reads the bits at the wrong moments and shows garbage.
> - A: Divider 32. "Double speed" was read as "half the rate": $16\,000\,000/(32\cdot104)=4807.7$.
> - B: `U2X0` was ignored, divider 16: $16\,000\,000/(16\cdot104)=9615.4$. This is the rate the program wanted.
> - C: The "+1" was forgotten: $16\,000\,000/(8\cdot103)=19\,417.5$.

### Q3 (slide 4)

The slide's table assumes a 1 MHz clock. It gives `UBRR0` = 25 for 2400 baud in normal mode, where $\text{BAUD}_{\text{real}}=f_{osc}/(16(\text{UBRR0}+1))$ and $\text{error}=(\text{BAUD}_{\text{real}}/\text{BAUD}_{\text{wanted}}-1)\cdot100\,\%$. What are the real baud rate and the error?

- A) Real rate 2403.8 baud, error +0.16 %.
- B) Real rate 2403.8 baud, error −0.16 %.
- C) Real rate 2500.0 baud, error +4.17 %.
- D) Real rate 2500.0 baud, error −4.17 %.

> [!success]- Answer
> **A.** $1\,000\,000/(16\cdot26)=1\,000\,000/416=2403.8$ baud.
> Error: $(2403.8/2400-1)\cdot100\,\%=+0.16\,\%$, well within ±2 %.
> The exact `UBRR0` is 25.04, so rounding to 25 changes almost nothing. At 9600 baud the exact value 5.51 becomes 6, the real rate is $10^6/(16\cdot7)=8928.6$ and the error is −7.0 %.
> - B: The slide's sign convention, (wanted − real)/wanted. It flips the sign.
> - C: The "+1" was forgotten: $10^6/(16\cdot25)=2500$, $(2500/2400-1)\cdot100\,\%=+4.17\,\%$.
> - D: Both mistakes: no "+1" (2500 baud) and the flipped sign: $(2400-2500)/2400=-4.17\,\%$.

### Q4 (slide 5)

An Uno ($f_{osc}$ = 16 MHz) must run at 1200 baud in normal mode: $\text{UBRR0}=f_{osc}/(16\,\text{BAUD})-1$, rounded. `UBRR0L` holds bits 7..0 and `UBRR0H` holds bits 11..8. Which values are right?

- A) `UBRR0` = 833 = `0x341`: `UBRR0H = 0x03`, `UBRR0L = 0x41`.
- B) `UBRR0` = 833 = `0x341`: `UBRR0H = 0x41`, `UBRR0L = 0x03`.
- C) `UBRR0` = 832 = `0x340`: `UBRR0H = 0x03`, `UBRR0L = 0x40`.
- D) `UBRR0` = 832 = `0x340`: `UBRR0H = 0x40`, `UBRR0L = 0x03`.

> [!success]- Answer
> **C.** $16\,000\,000/(16\cdot1200)-1=833.33-1=832.33\to832$, and $832=3\cdot256+64$ = `0x340`.
> High byte `832 >> 8` = 3, so `UBRR0H = 0x03`. Low byte `832 & 0xFF` = 64, so `UBRR0L = 0x40`.
> `UBRR0L` alone cannot hold 832: it keeps only 64, and the rate becomes $16\,000\,000/(16\cdot65)=15\,385$ baud.
> - A: The "−1" was forgotten: 833.33 → 833 = `0x341`.
> - B: No "−1" (833), and the two bytes swapped: the low byte went into `UBRR0H`.
> - D: The right value, but the two bytes swapped: the high byte belongs in `UBRR0H`.

## 3. Control and status registers (slides 6-9)

### Q5 (slide 6)

![[cmpe453_lecture_05_2_lecture5_2_p006.jpg]]

Right after reset you read `UCSR0A`. Use the "Initial Value" row of the figure. Careful: the slide's text "0 → Data reception is in progress" for `RXC0` is a slide error. In the datasheet, `RXC0` = 1 means an unread byte waits in the receive buffer, and `RXC0` = 0 means there is none. What is the value, and what does it tell you?

- A) `0x04`. `UDR0` is empty, a byte can be loaded. A byte is being received right now. Normal speed.
- B) `0x20`. `UDR0` is empty, a byte can be loaded. A byte is being received right now. Normal speed.

- D) `0x20`. `UDR0` is empty, a byte can be loaded. No received byte is waiting. Normal speed.

> **D.** Only bit 5 (`UDRE0`) has the initial value 1: `0b00100000` = `0x20`.

### Q6 (slide 7)

![[cmpe453_lecture_05_2_lecture5_2_p007.jpg]]

A student writes `UDR0 = 'A';` and in the next line `x = UDR0;`. Nothing is connected to RxD. Is `x` equal to `'A'`?

- A) No. The write goes into TXB and is sent on TxD. The read returns RXB, the last received byte.
- B) Yes. `UDR0` is one 8-bit register, and a read returns the value that was just written into it.
- C) Yes, but only after the frame has left TxD. Then `UDR0` holds the sent byte for reading.
- D) No. `UDR0` is a write-only register, so every read of it returns 0 and not the byte.

> [!success]- Answer
> **A.** The name `UDR0` stands for two buffers at one I/O address. Writing loads TXB, reading returns RXB.
> RXB holds the last byte that came in on RxD, 0 after reset if nothing has arrived. `x` is `'A'` only with a wire from TxD to RxD and a wait for `RXC0`.
> - B: The figure shows two rows, RXB for read and TXB for write. They are separate buffers.
> - C: A sent byte never moves into RXB. The transmitter and the receiver are separate.
> - D: The figure marks the bits R/W. The read is allowed; it returns RXB, which is 0 here only because nothing has arrived.

### Q7 (slide 8)

A data logger only listens. It switches the receiver on and enables the receive-complete interrupt. The transmitter stays off. In `UCSR0B`: `RXCIE0` is bit 7, `RXEN0` is bit 4, `TXEN0` is bit 3. Which value is right, and what happens to PD0 (RxD) and PD1 (TxD)?

- A) `UCSR0B = 0x88`. PD0 becomes RxD and PD1 becomes TxD. Both pins belong to the USART.
- B) `UCSR0B = 0x90`. PD0 becomes RxD and PD1 becomes TxD. Both pins belong to the USART.
- C) `UCSR0B = 0x90`. PD0 becomes RxD. PD1 stays a normal port pin under `DDRD` and `PORTD`.
- D) `UCSR0B = 0x88`. PD0 becomes RxD. PD1 stays a normal port pin under `DDRD` and `PORTD`.

> [!success]- Answer
> **C.** `UCSR0B = (1 << RXCIE0) | (1 << RXEN0);` = `0b10000000 | 0b00010000` = `0b10010000` = `0x90`.
> `RXEN0` takes over PD0 as RxD. `TXEN0` = 0, so PD1 stays a normal port pin. The interrupt also needs `sei()`.
> - A: `RXEN0` and `TXEN0` mixed up: bit 3 instead of bit 4 gives `0b10001000` = `0x88`. And PD1 is taken only by `TXEN0`, which is 0.
> - B: The value is right, but each enable bit takes only its own pin. With `TXEN0` = 0, PD1 stays free.
> - D: The pins are right, but bit 3 is `TXEN0`. The receiver enable is bit 4.

### Q8 (slide 9)

In `UCSR0C`: `UPM01:00` are bits 5:4 (parity: 00 none, 10 even, 11 odd), `USBS0` is bit 3 (0 = one stop bit, 1 = two), `UCSZ01:00` are bits 2:1. With `UCSZ02` = 0, `UCSZ01:00` = 00, 01, 10, 11 give 5, 6, 7, 8 data bits. Give `UCSR0C` for (a) 7 data bits, no parity, 1 stop bit, and (b) 8 data bits, even parity, 2 stop bits.

- A) (a) `0x02`, (b) `0x3E`
- B) (a) `0x04`, (b) `0x2E`
- C) (a) `0x02`, (b) `0x2E`
- D) (a) `0x04`, (b) `0x3E`

> [!success]- Answer
> **B.** (a) 7 bits is `UCSZ01:00` = 10, so only bit 2: `0b00000100` = `0x04`.
> (b) `UPM01` (bit 5) for even parity, `USBS0` (bit 3), `UCSZ01` and `UCSZ00` (bits 2, 1): `0b00101110` = `0x2E`.
> `UCSZ02` (in `UCSR0B`) stays 0 in both cases. It is 1 only for 9-bit frames.
> - A: Both slips: in (a) the code 10 was written into bits 1:0, not bits 2:1 (`0x02`), and in (b) the odd-parity code 11 was used: bit 4 also set, `0x3E`.
> - C: (b) is right, but in (a) the code 10 was written into bits 1:0 and not shifted to bits 2:1: `0b00000010` = `0x02`.

## 4. The loopback task (slides 10-15)

### Q9 (slide 10)

The task: (1) send a greeting, (2) receive a byte, (3) send the same byte back, (4) go to step 2. The terminal does not print typed keys by itself. What would the user see (i) if step 4 went back to step 1, and (ii) if step 3 were removed?

- A) (i) The greeting appears again after every typed key. (ii) After the greeting the terminal stays empty.
- B) (i) Nothing changes: the greeting goes out only at reset. (ii) After the greeting the terminal stays empty.
- C) (i) The greeting appears again after every typed key. (ii) The typed keys still appear, but only once each.
- D) (i) Nothing changes: the greeting goes out only at reset. (ii) The typed keys still appear, but only once each.

> [!success]- Answer
> **A.** (i) Step 1 would run in every pass, so the greeting is sent after each received byte. The terminal fills with greetings.
> (ii) The AVR still receives every byte but sends nothing back. The terminal does not print typed keys, so it stays empty.
> - B: Step 1 is code in the loop now. Going back to it runs it again; reset has nothing to do with it.
> - C: (i) is right, but what you see on the terminal is the AVR's echo. Without step 3 there is no echo.
> - D: Both mistakes: step 1 would run again in every pass, and without the echo nothing appears.

### Q11 (slides 12-13)

The computer sends `'A'` = `0x41` to the AVR at 9600 baud, 8N1 (1 start bit, 8 data bits, 1 stop bit). Which flag tells the AVR that the byte has arrived, and how long does one frame take?

### Q12 (slides 14-15)

The echo loop is `while (1) { c = receiveByte(); transmitByte(c); }`. `transmitByte` waits for `UDRE0` = 1 and then writes `UDR0`. The user types `A` and `B` very fast, so `B` starts to arrive while the echo of `A` is still going out. Is `B` lost?

- A) Yes. `transmitByte` waits until the frame of `A` has left TxD, and during this wait `B` is overwritten.
- B) Yes. TX and RX share `UDR0`, so writing the echo of `A` into `UDR0` destroys the received `B`.

> **C.** `transmitByte('A')` finds `UDRE0` = 1, writes `UDR0` and returns at once. It does not wait for the frame to leave the pin.

> Transmitter and receiver are separate hardware: the echo of `A` goes out on TxD while `B` comes in on RxD.
> - A: That is waiting for `TXC0`, not `UDRE0`. And even a 1.04 ms wait would not lose `B`.
> - B: A write goes into TXB, a read comes from RXB. They only share the address.
> - D: "Not lost" is right, but the reason is wrong: `transmitByte` does not wait for the frame to finish.

## 6. The same in the Arduino language (slide 18)

### Q15 (slide 18)

An Arduino sketch calls `Serial.write()` once in every pass of `loop()` at 9600 baud, 8N1 (10 bits per character). It also tests `Serial.available()` before `Serial.read()`, while `receiveByte()` has no such test. (a) How many characters per second can the wire carry at most? (b) Why the test?

> [!success]- Answer


Trace `printString("OK\r\n");`. ASCII: `'O'` = `0x4F`, `'K'` = `0x4B`. Which bytes are sent, and what is `i` when the loop ends?

## 8. Turn on LED number n (slides 22-24)

### Q18 (slide 22)

A program turns on one of 6 LEDs from an index the user types. It allows only the index values 2 to 7, with the LED on PD$n$. The USART is on with `RXEN0` and `TXEN0` set. Why are the indexes 0 and 1 not used for LEDs?

- D) Greeting: with every prompt. Prompt: 3 times.

> [!success]- Answer
> **B.** The greeting is before the loop: once.

### Q20 (slide 24)

The LED on PD3 is on (`PORTD` bit $n$ drives PD$n$). The user types `6`. The code runs `serialCharacter = serialCharacter - 0x30;` and then `PORTD = (1 << serialCharacter);`. Which value does `PORTD` get, and what happens to the LED on PD3?

- A) `PORTD` = `0x20` (`0b00100000`). The LED on PD3 stays on.
- B) `PORTD` = `0x40` (`0b01000000`). The LED on PD3 stays on.
- C) `PORTD` = `0x20` (`0b00100000`). The LED on PD3 goes off.
- D) `PORTD` = `0x40` (`0b01000000`). The LED on PD3 goes off.

> [!success]- Answer
> **D.** `'6'` = `0x36`, and `0x36 - 0x30` = 6. `1 << 6` = `0b01000000` = `0x40`: the LED on PD6.
> The `=` writes all 8 bits, so bit 3 becomes 0 and the LED on PD3 goes off. Only one LED is on at a time.
> Without the subtraction the shift would be `1 << 0x36` = `1 << 54`, far outside the 8 bits of the port.
> - A: Both mistakes: bits counted from 1 (`1 << 6` read as the sixth bit, `0x20`), and `=` treated like `|=`.
> - B: The value is right, but `=` is not `|=`. It clears every bit that is 0 in `0x40`, also bit 3.
> - C: `1 << 6` sets bit 6, the seventh bit from the right. `0x20` is `1 << 5`.
