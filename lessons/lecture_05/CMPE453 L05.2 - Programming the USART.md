# CMPE 453 · Lecture 5.2 · Programming the USART

> [!summary] In short
> - Four steps: set the baud rate, enable TX/RX, to send wait for `UDRE0` then write `UDR0`, to receive wait for `RXC0` then read `UDR0`.
> - $\text{UBRR0}=f_{osc}/(16\,\text{BAUD})-1$ (normal) or $f_{osc}/(8\,\text{BAUD})-1$ (double speed, `U2X0` = 1), rounded.
> - Uno, 16 MHz, 9600 baud: `UBRR0` = 103. The slide's table is for 1 MHz.
> - `UCSR0B = 0x18` switches TX and RX on. `UCSR0C = 0x06` is 8N1.
> - The PC sends ASCII: `'5'` is `0x35`. Subtract `'0'` to get the number.

## 1. Four steps to use the UART (slide 2)
![[cmpe453_lecture_05_2_lecture5_2_p002.jpg]]

**Notes.**
1. **Set the baud rate** (`UBRR0H`, `UBRR0L`, and `U2X0` for double speed).
2. **Enable** transmission and/or reception (`TXEN0`, `RXEN0` in `UCSR0B`).
3. **To transmit**: wait until the UART is ready (`UDRE0` = 1), then load the data into `UDR0`.
4. **To receive**: check that data has arrived (`RXC0` = 1), then read it from `UDR0`.

You write the control bits. The hardware writes the flags.

> [!question]- Check (slide 2): A program only sends text and never receives. Which of the four steps does it still need, and how often does each one run?
> It needs steps I, II and III. Step IV is not needed, and in step II only `TXEN0` is set (`RXEN0` stays 0, so PD0 stays a normal port pin).
> Steps I and II run **once**, at the start of the program.
> Step III runs **for every byte**: wait for `UDRE0` = 1, then write the byte to `UDR0`.

## 2. Setting the baud rate: UBRR0 (slides 3-5)
![[cmpe453_lecture_05_2_lecture5_2_p003.jpg]]
![[cmpe453_lecture_05_2_lecture5_2_p004.jpg]]
![[cmpe453_lecture_05_2_lecture5_2_p005.jpg]]

**Notes.** $f_{osc}$ is the CPU clock in Hz. `UBRR0` is a whole number from 0 to 4095 (12 bits). Round to the nearest whole number.

| Mode | Baud rate | `UBRR0` value |
|---|---|---|
| Async normal (`U2X0` = 0) | $\dfrac{f_{osc}}{16(\text{UBRR0}+1)}$ | $\dfrac{f_{osc}}{16\,\text{BAUD}}-1$ |
| Async double speed (`U2X0` = 1) | $\dfrac{f_{osc}}{8(\text{UBRR0}+1)}$ | $\dfrac{f_{osc}}{8\,\text{BAUD}}-1$ |
| Synchronous master | $\dfrac{f_{osc}}{2(\text{UBRR0}+1)}$ | $\dfrac{f_{osc}}{2\,\text{BAUD}}-1$ |

After rounding, the real rate differs from the wanted one:

$$\text{error}=\left(\frac{\text{BAUD}_{\text{real}}}{\text{BAUD}_{\text{wanted}}}-1\right)\cdot100\,\%$$

Keep the error within about ±2 %. Always compute the real rate from the **rounded** `UBRR0`.

> [!example] Slide 4, at 1 MHz, 9600 baud
> - Normal: $10^6/(16\cdot9600)-1=5.51\to6$. Real: $10^6/(16\cdot7)=8928$. Error 7 % (too slow), not usable.
> - Double speed: $10^6/(8\cdot9600)-1=12.02\to12$. Real: $10^6/(8\cdot13)=9615$. Error 0.16 %, fine.

> [!example] The Uno, 16 MHz, 9600 baud
> $16\,000\,000/(16\cdot9600)-1=103.17\to103$. Real: $16\,000\,000/(16\cdot104)=9615.4$. Error +0.16 %.

`UBRR0L` holds bits 7..0, the low four bits of `UBRR0H` hold bits 11..8. Bits 15..12 are reserved. Split a value with `>> 8` (high byte) and `& 0xFF` (low byte). Example: 416 = `0x1A0`, so `UBRR0H = 0x01`, `UBRR0L = 0xA0`.

> [!warning] Watch out
> - **The slide's table is for a 1 MHz clock** and does not say so. At 16 MHz: 9600 → 103 (normal) or 207 (double), 4800 → 207 or 416, 2400 → 416 or 832.
> - The slide computes the error as (wanted − real)/wanted, which flips the sign. Its "0.15 %" is 0.16 %.
> - `UBRR0L = 416;` keeps only the low byte, 160.
> - The slide writes "UBBR0". The name is `UBRR0`.
> - "USART is sync communication and requires clock signal" holds only in synchronous mode. The asynchronous mode (UART) needs no clock wire.

> [!info] Where the two formulas come from (beyond the slides)
> The USART makes its bit clock by dividing the CPU clock. First a counter divides $f_{osc}$ by $(\text{UBRR0}+1)$. The "+1" is there because the counter counts from `UBRR0` down to 0, which is $\text{UBRR0}+1$ steps. Then a fixed divider follows: 16 in normal mode, 8 in double speed mode. The receiver uses these 16 (or 8) clock ticks to look at each bit several times near its middle.
>
> So in normal mode:
>
> $$\text{BAUD}=\frac{f_{osc}}{16\,(\text{UBRR0}+1)}$$
>
> Solve for `UBRR0`. Multiply both sides by $(\text{UBRR0}+1)$ and divide by BAUD:
>
> $$\text{UBRR0}+1=\frac{f_{osc}}{16\,\text{BAUD}}$$
>
> Subtract 1:
>
> $$\text{UBRR0}=\frac{f_{osc}}{16\,\text{BAUD}}-1$$
>
> Double speed mode is the same with 8 in place of 16. A bigger `UBRR0` gives a **slower** baud rate. With 8 the exact value is about twice as large, so rounding to a whole number changes it less. That is why double speed mode often has the smaller error.

> [!question]- Check (slide 3): An Uno (16 MHz) is set up for 9600 baud in normal mode, `UBRR0` = 103. By mistake the program also sets `U2X0` = 1. Which baud rate does the Uno really use, and what does the terminal (still at 9600) show?
> With `U2X0` = 1 the divider is 8, not 16:
> $$\text{BAUD}=\frac{16\,000\,000}{8\cdot(103+1)}=\frac{16\,000\,000}{832}=19\,230.8$$
> That is twice the wanted rate (about 19 200 baud). The terminal samples the bits at the wrong moments and shows garbage.
> Fix: clear `U2X0`, or keep it and use `UBRR0` = 207.

> [!question]- Check (slide 4): The slide's table (1 MHz clock) gives `UBRR0` = 25 for 2400 baud in normal mode. Compute the real baud rate and the error. Why is normal mode fine here, but not for 9600 baud?
> Real rate: $1\,000\,000/(16\cdot(25+1))=1\,000\,000/416=2403.8$ baud.
> Error: $(2403.8/2400-1)\cdot100\,\%=+0.16\,\%$. This is well within ±2 %.
> Reason: the exact value is 25.04, so rounding to 25 changes almost nothing. For 9600 baud the exact value is 5.51 and it becomes 6. The divider $\text{UBRR0}+1$ is then 7 and not 6.51, so the real rate is $1\,000\,000/(16\cdot7)=8928.6$ baud. The error is $(8928.6/9600-1)\cdot100\,\%=-7.0\,\%$.
> Small `UBRR0` values make rounding expensive.

> [!question]- Check (slide 5): An Uno (16 MHz) must run at 1200 baud in normal mode. Compute `UBRR0` and give the values of `UBRR0H` and `UBRR0L` in hex. Why can you not write the value into `UBRR0L` alone?
> $\text{UBRR0}=16\,000\,000/(16\cdot1200)-1=833.33-1=832.33\to832$.
> $832=3\cdot256+64$ = `0x340`.
> High byte: `832 >> 8` = 3, so `UBRR0H = 0x03`. Low byte: `832 & 0xFF` = 64, so `UBRR0L = 0x40`.
> `UBRR0L` has only 8 bits (0 to 255). Writing 832 into it keeps only 64. Then the baud rate would be $16\,000\,000/(16\cdot65)=15\,385$ baud, far from 1200.
> Real rate with 832: $16\,000\,000/(16\cdot833)=1200.5$ baud, error +0.04 %.

## 3. Control and status registers (slides 6-9)
![[cmpe453_lecture_05_2_lecture5_2_p006.jpg]]
![[cmpe453_lecture_05_2_lecture5_2_p007.jpg]]
![[cmpe453_lecture_05_2_lecture5_2_p008.jpg]]
![[cmpe453_lecture_05_2_lecture5_2_p009.jpg]]

**Notes.**

| Register | Bit | Meaning when 1 |
|---|---|---|
| `UCSR0A` | 7 `RXC0` | a new byte is in `UDR0`, ready to be read. Reading `UDR0` clears it |
| `UCSR0A` | 5 `UDRE0` | `UDR0` is empty, new data can be loaded. Reset value 1 |
| `UCSR0A` | 1 `U2X0` | double speed mode (0 = normal) |
| `UCSR0B` | 4 `RXEN0` | receiver enabled, takes over PD0 as RxD |
| `UCSR0B` | 3 `TXEN0` | transmitter enabled, takes over PD1 as TxD |

`UDR0` (slide 7): the transmit buffer (TXB) and the receive buffer (RXB) share one I/O address. Writing `UDR0` loads TXB. Reading `UDR0` returns RXB.

Character size (slide 9): `UCSZ01:0` in `UCSR0C` and `UCSZ02` in `UCSR0B`.

| `UCSZ02` | `UCSZ01` | `UCSZ00` | Size |
|---|---|---|---|
| 0 | 0 | 0 | 5-bit |
| 0 | 0 | 1 | 6-bit |
| 0 | 1 | 0 | 7-bit |
| 0 | 1 | 1 | **8-bit** |
| 1 | 1 | 1 | 9-bit |

`UCSR0B = (1 << TXEN0) | (1 << RXEN0);` = `0b00011000` = `0x18`. `UCSR0C = (1 << UCSZ01) | (1 << UCSZ00);` = `0b00000110` = `0x06`, which is 8N1 and also the reset value.

> [!warning] Slide error
> The slide says for `RXC0`: "0 → data reception is in progress". Correct: `RXC0` = 0 means there is **no unread byte**. Usually nothing is arriving at all.

> [!warning] Slide error
> The title of slide 9 says "USCR0C". The register is `UCSR0C`. Slides 6 and 8 write "UDRE", "RXEN" and "TXEN" without the 0. In C code the names are `UDRE0`, `RXEN0` and `TXEN0`.

> [!info] The other bits in the three figures (beyond the slides)
> The slides show all 8 bits of each register but explain only a few. The "n" in the figures is the USART number. The ATmega328P has only USART0, so n = 0.
>
> | Register | Bit | Meaning |
> |---|---|---|
> | `UCSR0A` | 6 `TXC0` | 1 = the whole frame has left the pin and `UDR0` holds no new byte |
> | `UCSR0A` | 4 `FE0`, 3 `DOR0`, 2 `UPE0` | error flags: frame error, data overrun (a byte was lost), parity error |
> | `UCSR0B` | 7 `RXCIE0` | 1 = call an interrupt routine when `RXC0` becomes 1 |
> | `UCSR0B` | 6 `TXCIE0`, 5 `UDRIE0` | interrupt enables for `TXC0` and `UDRE0` |
> | `UCSR0B` | 2 `UCSZ02` | third character-size bit, 1 only for 9-bit frames |
> | `UCSR0C` | 7:6 `UMSEL01:00` | 00 = asynchronous (UART) |
> | `UCSR0C` | 5:4 `UPM01:00` | parity: 00 none, 10 even, 11 odd |
> | `UCSR0C` | 3 `USBS0` | stop bits: 0 = one, 1 = two |
>
> `UDRE0` and `TXC0` are not the same. `UDRE0` = 1 means the buffer `UDR0` is free, even if the previous frame is still on the wire. `TXC0` = 1 means the wire is quiet. To send the next byte you wait for `UDRE0`.
>
> The bits with "EN" or "IE" in the name are switches that you set. `RXC0`, `TXC0` and `UDRE0` are flags that the hardware sets. `TXEN0` and `TXC0` differ by one letter only.

> [!question]- Check (slide 6): Right after reset you read `UCSR0A`. Use the "Initial Value" row of the figure to give the value in binary and hex. What does it tell you about the transmitter, the receiver and the speed mode?
> Only bit 5 (`UDRE0`) has the initial value 1. So `UCSR0A` = `0b00100000` = `0x20`.
> `UDRE0` = 1: `UDR0` is empty, a byte can be loaded for sending.
> `RXC0` = 0: no received byte is waiting.
> `U2X0` = 0: normal speed mode, so the formula with 16 applies.

> [!question]- Check (slide 7): A student writes `UDR0 = 'A';` and in the next line `x = UDR0;`. Is `x` equal to `'A'`? Explain with the figure.
> No. The name `UDR0` stands for two different buffers at one address.
> The write goes into the transmit buffer TXB, and `'A'` is sent out on TxD.
> The read returns the receive buffer RXB, which holds the last byte that came in on RxD (0 after reset if nothing has arrived).
> `x` is `'A'` only if a wire connects TxD back to RxD and the program waits for `RXC0` before it reads.

> [!question]- Check (slide 8): A data logger only listens. It must switch the receiver on and enable the receive-complete interrupt. The transmitter stays off. Which bits of `UCSR0B` do you set, and what is the value in hex? What happens to pins PD0 and PD1?
> Set `RXCIE0` (bit 7) and `RXEN0` (bit 4).
> `UCSR0B = (1 << RXCIE0) | (1 << RXEN0);` = `0b10000000 | 0b00010000` = `0b10010000` = `0x90`.
> PD0 becomes RxD, whatever `DDRD` says. `TXEN0` = 0, so PD1 stays a normal port pin.
> The interrupt routine also needs the global interrupt enable `sei()` (beyond the slides).

> [!question]- Check (slide 9): Give `UCSR0C` in hex for (a) 7 data bits, no parity, 1 stop bit, and (b) 8 data bits, even parity, 2 stop bits (use the info box above for parity and stop bits). What must `UCSZ02` be in both cases?
> (a) 7-bit is `UCSZ01` = 1, `UCSZ00` = 0. Only bit 2 is set: `UCSR0C = (1 << UCSZ01);` = `0b00000100` = `0x04`.
> (b) 8-bit: `UCSZ01` (bit 2) and `UCSZ00` (bit 1). Even parity: `UPM01` (bit 5). Two stop bits: `USBS0` (bit 3).
> `0b00100000 | 0b00001000 | 0b00000100 | 0b00000010` = `0b00101110` = `0x2E`.
> `UCSZ02` (in `UCSR0B`) must be 0 in both cases. It is 1 only for 9-bit frames. `UCSR0B = 0x18` already leaves it at 0.

**Notes.** The task: (1) send a greeting to the computer, (2) receive a byte from the computer, (3) send the same byte back, (4) go to step 2.

The pictures show it: the AVR sends "Hello Computer! This is AVR". The computer sends `A`, the AVR sends `A` back. Then `B`, and `B` comes back. Each byte returns before the next one is read. The terminal does not print typed keys by itself, so what you see is the AVR's echo.

> [!question]- Check (slide 10): Step 4 says "go to step 2", not "go to step 1". What would the user see if the program went back to step 1? And what would the user see if step 3 were removed?
> Back to step 1: the greeting is sent again after every typed key. The terminal fills with greetings.
> Without step 3: the AVR still receives every byte, but sends nothing back. After the greeting the terminal stays empty, because the terminal does not print typed keys by itself.

> [!question]- Check (slide 11): In the figure, the black arrow goes from the AVR to the computer and the red arrow goes back. Which ATmega328P pin drives the black arrow, which pin listens to the red arrow, and which enable bit belongs to each?
> Black arrow (AVR sends): TxD = PD1 (Uno pin D1), switched on by `TXEN0`.
> Red arrow (AVR receives): RxD = PD0 (Uno pin D0), switched on by `RXEN0`.
> The greeting "Hello Computer! This is AVR" travels on the black arrow, so only the transmitter is needed for it.

> [!question]- Check (slides 12-13): The computer sends `A` (slide 12) and the AVR sends it back (slide 13). Which byte value travels? Which flag tells the AVR that `A` has arrived, and what clears this flag? How long does one frame take at 9600 baud, 8N1?
> `'A'` is ASCII 65 = `0x41`.
> When the whole frame is in, the hardware sets `RXC0` = 1. Reading `UDR0` clears it.
> One 8N1 frame has 1 start bit + 8 data bits + 1 stop bit = 10 bits. Time: $10/9600\ \text{s}=1.04$ ms.
> The echo needs another 1.04 ms, so `A` is back at the computer about 2.1 ms after its start bit left the computer.

> [!question]- Check (slides 14-15): The user types `A` and `B` very fast, so `B` starts to arrive while the echo of `A` is still going out. Is `B` lost? Trace the loop.
> No.
> 1. `receiveByte()` returns `A` when `RXC0` = 1.
> 2. `transmitByte('A')` finds `UDRE0` = 1, writes `UDR0` and returns at once. It does not wait until the frame has left the pin.
> 3. The program is back in `receiveByte()` and waits for `RXC0`. `B` needs about 1.04 ms to arrive, so the program is ready long before.
> 4. The transmitter and the receiver are separate hardware. The echo of `A` goes out on TxD while `B` comes in on RxD.

## 5. initUSART, transmitByte, receiveByte (slides 16-17)
![[cmpe453_lecture_05_2_lecture5_2_p016.jpg]]
![[cmpe453_lecture_05_2_lecture5_2_p017.jpg]]

**Notes.**

```c
#include <avr/io.h>
#include "USART.h"
#include <util/setbaud.h>
void initUSART(void)
{
  /* requires BAUD, defined in USART.h */
  UBRR0H = UBRRH_VALUE;                   /* defined in setbaud.h */
  UBRR0L = UBRRL_VALUE;
  /* select normal or double speed mode */
#if USE_2X
  UCSR0A |= (1 << U2X0);
#else
  UCSR0A &= ~(1 << U2X0);
#endif
  UCSR0B = (1 << TXEN0) | (1 << RXEN0);   /* enable USART transmitter/receiver */
  UCSR0C = (1 << UCSZ01) | (1 << UCSZ00); /* 8 data bits */
}
```

`<util/setbaud.h>` reads `F_CPU` and `BAUD` at compile time and defines `UBRRH_VALUE`, `UBRRL_VALUE` and `USE_2X` (1 if normal mode would miss the baud rate by more than 2 %). `BAUD` must be defined before the include. At 16 MHz and 9600 baud: `UBRR0H` = 0, `UBRR0L` = 103 = `0x67`, `U2X0` = 0.

```c
void transmitByte(uint8_t data)
{
  loop_until_bit_is_set(UCSR0A, UDRE0);   /* wait for empty transmit buffer */
  UDR0 = data;                            /* send data */
}
uint8_t receiveByte(void)
{
  loop_until_bit_is_set(UCSR0A, RXC0);    /* wait for incoming data */
  return UDR0;                            /* return register value */
}
```

Both functions **poll**: they wait in a loop on a flag. `receiveByte` waits forever if no byte comes.

> [!warning] Watch out
> - `transmitByte` waits for `UDRE0`, `receiveByte` waits for `RXC0`. Swapping them is a classic bug.
> - If `TXEN0` is not set, nothing appears on TxD.
> - The receive buffer holds only 2 bytes. If the program is busy for long (a `_delay_ms(1000)`), bytes are lost.

> [!info] What the wait macro does, and the interrupt alternative (beyond the slides)
> `loop_until_bit_is_set(UCSR0A, UDRE0);` is the same as
>
> ```c
> while (!(UCSR0A & (1 << UDRE0))) { }
> ```
>
> `(1 << UDRE0)` is the mask `0b00100000`. The `&` keeps only bit 5 of `UCSR0A`. While that bit is 0 the result is 0, `!0` is true, and the empty loop runs again. When the hardware sets the bit, the loop ends.
>
> The slides only poll. The USART can also start an interrupt routine when a byte arrives. Then the main loop does not have to wait:
>
> ```c
> ISR(USART_RX_vect)            /* runs when RXC0 becomes 1 */
> {
>   rxByte = UDR0;              /* reading UDR0 clears RXC0 */
>   rxFlag = 1;
> }
> ```
>
> Switch it on after `initUSART()` with `UCSR0B |= (1 << RXCIE0);` and `sei();`. The `|=` takes `UCSR0B` from `0x18` to `0b10011000` = `0x98` and keeps `TXEN0` and `RXEN0`. `rxByte` and `rxFlag` must be `volatile` globals. Interrupts come later in the course.

> [!question]- Check (slide 16): `F_CPU` is 16 MHz and `USART.h` defines `BAUD` as 57600. Compute the normal-mode `UBRR0` and its error. Which branch of `#if USE_2X` is compiled, and which values go into `UBRR0H` and `UBRR0L`?
> Normal mode: $16\,000\,000/(16\cdot57\,600)-1=17.36-1=16.36\to16$.
> Real rate: $16\,000\,000/(16\cdot17)=58\,823.5$. Error: $(58\,823.5/57\,600-1)\cdot100\,\%=+2.12\,\%$.
> This is more than 2 %, so `setbaud.h` sets `USE_2X` to 1. The first branch is compiled: `UCSR0A |= (1 << U2X0);`.
> Double speed: $16\,000\,000/(8\cdot57\,600)-1=34.72-1=33.72\to34$.
> Real rate: $16\,000\,000/(8\cdot35)=57\,142.9$. Error: $-0.79\,\%$.
> So `UBRR0H` = 0 and `UBRR0L` = 34 = `0x22`.

> [!question]- Check (slide 17): Someone deletes the line `loop_until_bit_is_set(UCSR0A, UDRE0);` from `transmitByte` and then sends "Hello" at 9600 baud. What arrives at the terminal, and why? How many CPU clock cycles does one frame last at 16 MHz?
> Most likely only "He" arrives, and the last three characters are lost (this follows from the datasheet; it is not tested on the board).
> One frame lasts $10/9600\ \text{s}=1.04$ ms. At 16 MHz that is $16\,000\,000\cdot10/9600\approx16\,667$ clock cycles. The loop that calls `transmitByte` needs only a few cycles per character, so all five writes come within the first frame.
> The transmitter has two places for a byte (beyond the slides): the shift register, which sends the bits on TxD, and the buffer `UDR0` in front of it.
> 1. `'H'`: `UDRE0` = 1, the write is accepted. The shift register is free, so `'H'` moves into it at once and the frame starts. The buffer is empty again, `UDRE0` = 1.
> 2. `'e'`: `UDRE0` = 1, the write is accepted. The shift register is busy with `'H'` for 1.04 ms, so `'e'` waits in the buffer. Now `UDRE0` = 0.
> 3. `'l'`, `'l'`, `'o'`: each write comes while `UDRE0` = 0. The slide says "do not load new data into UDR0" in this state. The transmitter ignores such a write (datasheet, beyond the slides), so these three characters never go out.
>
> When `'H'` is finished, `'e'` moves into the shift register and is sent. Then the line is quiet.
> The wait line slows the program down to the speed of the wire.

## 6. The same in the Arduino language (slide 18)
![[cmpe453_lecture_05_2_lecture5_2_p018.jpg]]

**Notes.** `Serial.begin(9600)` does what `initUSART` does. `Serial.available()` checks `RXC0`, `Serial.read()` reads the byte, `Serial.write()` sends one.

The sketch: a button on pin 8 (with pull-up) and an LED on pin 13. A received `'1'` switches the LED on, `'0'` switches it off. In every pass of `loop()` it sends `'0'` if the button is not pressed and `'1'` if it is pressed, so the terminal is flooded with characters.

Two Unos with this sketch, TX of each to RX of the other and GNDs joined, make the Elif-and-Damla link of [[CMPE453 L05.1 - UART frame]].

> [!warning] Watch out
> `if (data_rcvd == '1')` compares. `if (data_rcvd = '1')` assigns and is always true.

> [!question]- Check (slide 18): (a) The sketch calls `Serial.write()` in every pass of `loop()`. At 9600 baud, 8N1, how many characters per second can the wire carry at most? (b) Why does the sketch test `Serial.available()` before `Serial.read()`, while `receiveByte()` has no such test?
> (a) One character is one frame of 10 bits. $9600/10=960$ characters per second. The loop cannot send faster than that, so the terminal gets about 960 times `'0'` or `'1'` every second.
> (b) `receiveByte()` blocks: it waits in a loop until `RXC0` = 1. That is fine for the echo program, which has nothing else to do.
> This sketch must also read the button and send its state in every pass. With `Serial.available()` it reads only when a byte is already there, and goes on at once when there is none. A blocking read would stop the button reports until the next byte arrives.

## 7. printString and the main program (slides 19-21)
![[cmpe453_lecture_05_2_lecture5_2_p019.jpg]]
![[cmpe453_lecture_05_2_lecture5_2_p020.jpg]]
![[cmpe453_lecture_05_2_lecture5_2_p021.jpg]]

**Notes.**

```c
void printString(const char myString[])
{
  uint8_t i = 0;
  while (myString[i]) {          /* strings end with a null character in C */
    transmitByte(myString[i]);
    i++;
  }
}
```

A C string ends with `'\0'` (value 0), which is "false", so the loop stops there.

```c
int main(void)
{
  char serialCharacter;
  initUSART();
  printString("Hello computer!\r\n");      /* to test */
  printString("This is AVR!\r\n");
  while (1) {
    serialCharacter = receiveByte();
    transmitByte(serialCharacter);
  }
  return 0;
}
```

To print a number, send its digits: `'0' + b / 100`, `'0' + (b / 10) % 10`, `'0' + b % 10`. `transmitByte(65);` shows `A`, not "65".

> [!warning] Watch out
> - End terminal lines with `"\r\n"`: carriage return (`0x0D`) and line feed (`0x0A`).
> - Slide 21's `#include <USART.c>` and the other library headers only work in the Arduino IDE with the library installed. With `avr-gcc`, compile `USART.c` alongside and include `"USART.h"`.

> [!question]- Check (slide 19): Trace `printString("OK\r\n");`. How many times is `transmitByte` called, and with which byte values? What is `i` when the loop ends, and why is the null character not sent?
> The array holds 5 bytes: `'O'` = `0x4F`, `'K'` = `0x4B`, `'\r'` = `0x0D`, `'\n'` = `0x0A`, `'\0'` = `0x00`.
> `i` = 0, 1, 2, 3: the byte is not zero, so the condition is true and the byte is sent. That is **4 calls**: `0x4F`, `0x4B`, `0x0D`, `0x0A`.
> `i` = 4: `myString[4]` is 0, which counts as false. The loop ends with `i` = 4, before `transmitByte` is called. So the null character is only the end mark and never goes on the wire.
> At 9600 baud the 4 frames take $4\cdot10/9600\ \text{s}=4.17$ ms.

> [!question]- Check (slides 20-21): (a) Match the lines of the pseudocode to the C lines of `main`. (b) How long does the greeting take at 9600 baud, 8N1? (c) Where is the CPU most of the time when nobody types?
> (a) "Initialize UART" is `initUSART();`. "Send Greetings" is the two `printString` calls. "receive byte" is `serialCharacter = receiveByte();`. "send same byte back" is `transmitByte(serialCharacter);`.
> (b) `"Hello computer!\r\n"` has 15 + 2 = 17 bytes. `"This is AVR!\r\n"` has 12 + 2 = 14 bytes. Together 31 bytes = 310 bits. $310/9600\ \text{s}=32.3$ ms.
> (c) Inside `receiveByte()`, in the loop `loop_until_bit_is_set(UCSR0A, RXC0);`. It tests `RXC0` again and again until a byte arrives. `return 0;` is never reached.

**Notes.** The AVR asks the laptop for an index, reads it, and turns on that LED out of 6 LEDs on PD2 to PD7. If the index is less than 2 or greater than 7 it sends "out of range".

Clean version of slide 24:

```c
#include <avr/io.h>
#include "USART.h"
int main(void)
{
  char c;
  DDRD |= 0b11111100;                  /* LEDs on PD2..PD7 (Uno D2..D7) */
  initUSART();                         /* PD0 = RXD, PD1 = TXD */
  printString("Hello Laptop!\r\n");
  printString("This is AVR.\r\n");
  while (1) {
    printString("Enter a number, from 2 to 7 and I will "
                "turn on corresponding LED\r\n");
    c = receiveByte();
    transmitByte(c);                   /* echo, so the user sees the key */
    printString("\r\n");
    if ((c < '2') || (c > '7')) {      /* '2' = 0x32, '7' = 0x37 */
      printString("The number you entered is out of range\r\n");
    } else {
      PORTD = (1 << (c - '0'));        /* '5' -> 5 -> 0b00100000 */
    }
  }
}
```

Typing `3` sends `0x33`. $\texttt{0x33}-\texttt{0x30}=3$, `1 << 3` = `0b00001000`, so `PORTD` = `0x08`: the LED on D3.

> [!warning] Problems in the slide's version
> - It writes `LED_PORT = (1 << serialCharacter);` and then `PORTD = LED_PORT;`: a detour through another port. `PORTD = (1 << n);` is enough.
> - `DDRD = 0xff` also makes PD0 (RxD) an output. It works only because `RXEN0` overrides PD0.
> - `PORTD = LED_PORT;` is printed at the left margin but is inside the `else` braces.
> - `printString("\n")` misses the `\r`.
> - Serial Monitor set to "Newline": typing `5` and Enter sends `'5'` and `'\n'` (`0x0A`). The LED lights, then "out of range" is printed. Choose "No line ending".

> [!question]- Check (slide 22): The task allows only the index values 2 to 7. Port D has 8 pins, PD0 to PD7. Why are the indexes 0 and 1 not used for LEDs?
> PD0 is RxD and PD1 is TxD. The program talks to the laptop over these two pins.
> When `RXEN0` and `TXEN0` are set, the USART takes over PD0 and PD1. The program can then no longer drive these two pins as LED outputs through `PORTD`.
> So only PD2 to PD7 (Uno pins D2 to D7) are free: 6 pins for 6 LEDs.

> [!question]- Check (slide 23): The pseudocode sends the greeting before `while(1)` and the prompt inside it. The user enters three numbers. How many times has the AVR sent the greeting and the prompt when it waits for the fourth number?
> Greeting: **once**. It is before the loop.
> Prompt: **4 times**. It is the first line of every pass: three passes are finished, and the fourth pass has sent its prompt and now waits in "Receive index value".
> If the prompt were before the loop, the user would see it only once.

> [!question]- Check (slide 24): The LED on PD3 is on. Now the user types `6`. Trace the slide's lines from `receiveByte()` to the port write. Which value does the port get in binary and hex, and what happens to the LED on PD3? What would happen without the line `serialCharacter = serialCharacter-0x30;`?
> `receiveByte()` returns `'6'` = `0x36`.
> Range test: `0x36 < 0x32` is false and `0x36 > 0x37` is false, so the `else` branch runs.
> `0x36 - 0x30 = 6`. Then `1 << 6` = `0b01000000` = `0x40`.
> `PORTD` = `0x40`: the LED on PD6 (Uno D6) is on. The `=` writes all 8 bits, so bit 3 becomes 0 and the LED on PD3 goes **off**. Only one LED is on at a time.
> Without the subtraction the shift would be `1 << 0x36` = `1 << 54`. That is far outside the 8 bits of the port, so no valid LED bit is set.

## Key formulas and terms
| Term | Meaning / formula |
|---|---|
| `UBRR0` | normal $f_{osc}/(16\,\text{BAUD})-1$, double $f_{osc}/(8\,\text{BAUD})-1$, rounded, 12 bits in `UBRR0H`:`UBRR0L` |
| Error | $(\text{real}/\text{wanted}-1)\cdot100\,\%$, keep within ±2 % |
| Uno, 16 MHz | 9600 → 103 (+0.16 %), 19 200 → 51, 38 400 → 25 |
| `UCSR0A` | `RXC0` (b7) byte received, `UDRE0` (b5) ready to send, `U2X0` (b1) double speed |
| `UCSR0B` | `RXEN0` (b4) takes PD0, `TXEN0` (b3) takes PD1, both: `0x18` |
| `UCSR0C` | `UCSZ01:00` = 11 is 8 bits, `0x06` = 8N1 (reset value) |
| `UDR0` | write = send (TXB), read = received byte (RXB) |
| Send | wait for `UDRE0`, write `UDR0` |
| Receive | wait for `RXC0`, read `UDR0` |
| ASCII digit | `'0'` + n, back with `c - '0'` |

## Check yourself
> [!question]- 1. 16 MHz, 19 200 baud, normal mode: `UBRR0`, real rate, error, and the C statements.
> $16\,000\,000/(16\cdot19\,200)-1=51.08\to$ **51**. Real: $16\,000\,000/832=19\,230.8$. Error **+0.16 %**.
> ```c
> UBRR0H = 0;
> UBRR0L = 51;
> UCSR0A &= ~(1 << U2X0);
> ```

> [!question]- 2. 8 MHz, 115 200 baud: is normal or double speed acceptable?
> Normal: $3.34\to3$, real 125 000, error +8.51 %. Double: $7.68\to8$, real 111 111, error −3.55 %. **Neither** is within ±2 %. Use 38 400 (UBRR0 = 12, +0.16 %).

> [!question]- 3. Which clock does the slide's table (9600 → 5.5 normal, 12.02 double) assume? Give `UBRR0H`/`UBRR0L` for 2400 baud at 16 MHz, normal mode.
> $(5.5+1)\cdot16\cdot9600\approx$ **1 MHz**. At 16 MHz: $415.67\to416=$ `0x1A0`: `UBRR0H = 0x01`, `UBRR0L = 0xA0`.

> [!question]- 4. Give `UCSR0B` and `UCSR0C` in hex for transmitter and receiver on, 8N1.
> `UCSR0B` = `0b00011000` = **`0x18`**. `UCSR0C` = **`0x06`**.

> [!question]- 5. Find three mistakes: `UCSR0B = (1 << RXEN0);` in init, `loop_until_bit_is_set(UCSR0A, RXC0);` in `transmitByte`, `loop_until_bit_is_clear(UCSR0A, RXC0);` in `receiveByte`.
> (1) `TXEN0` is missing, the transmitter is off. (2) `transmitByte` must wait for `UDRE0`. (3) `receiveByte` must use `loop_until_bit_is_set` on `RXC0`, otherwise it returns at once with no byte.

> [!question]- 6. Explain: (a) the terminal shows garbage instead of "Hello". (b) Typing 5 and Enter lights LED 5 and then prints "out of range".
> (a) Baud-rate mismatch, or `F_CPU` does not match the real clock. (b) The monitor also sends `'\n'` (`0x0A`), which is below `0x32`.
