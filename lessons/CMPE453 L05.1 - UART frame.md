# CMPE 453 · Lecture 5.1 · Serial communication: the UART frame

> [!summary] In short
> - Serial = the bits of a byte go one after the other on one wire. Three protocols in the course: USART, SPI, I2C.
> - 8N1 frame: line idle at 1, start bit 0, 8 data bits **LSB first**, stop bit 1. That is 10 line bits per byte.
> - Decode: drop start and stop, reverse the 8 data bits.
> - Baud = line bits per second. Bit time = 1/baud (9600 baud: 104.2 µs, 960 bytes/s).
> - There is no clock wire. Both sides must agree on the baud rate and the frame.
> - On the Uno: RxD = PD0 = D0, TxD = PD1 = D1. TX goes to RX, GND to GND.

## 1. Serial communication and its three protocols (slides 2-3)
![[cmpe453_lecture_05_1_lecture5_1_p002.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p003.jpg]]

**Notes.** In serial communication the sender puts the bits on **one** data line, one at a time. Parallel would use 8 wires. USART is the simplest way to connect an AVR to a computer or to another microcontroller.

| | UART | SPI | I2C |
|---|---|---|---|
| Wires (plus GND) | TX, RX | MOSI, MISO, SCK, SS | SDA, SCL |
| Clock wire | no (agreed baud rate) | yes (SCK) | yes (SCL) |

**Simplex**: one direction only. **Half duplex**: both directions, one at a time on a shared wire. **Full duplex**: both directions at the same time on separate wires. UART has a TX and an RX wire, so it is full duplex.

> [!question]- Check (slide 2): A device must move a block of 32 bytes. A parallel link with 8 data wires moves one whole byte every 50 µs. A serial link moves one bit every 50 µs (count only the data bits). How long does each link need, and what does the serial link save?
> Parallel: $32\times 50\ \text{µs}=1600\ \text{µs}=1.6$ ms.
> Serial: $32\times 8=256$ bits, $256\times 50\ \text{µs}=12800\ \text{µs}=12.8$ ms.
> Serial is 8 times slower at the same bit time, but it needs 1 data wire instead of 8. Fewer wires and fewer pins are the reason all three protocols of the slide (USART, SPI, I2C) are serial.

> [!question]- Check (slide 3): The S and the A in USART stand for synchronous and asynchronous. Which extra wire does the synchronous mode need, and what replaces this wire when the AVR talks to a computer in asynchronous mode?
> Synchronous mode needs a **clock wire** (pin XCK). The clock tells the receiver when to read each bit.
> Asynchronous mode has no clock wire. Two things replace it: both sides agree on the **baud rate** in advance, and every byte begins with a **start bit** that tells the receiver when to start counting bit times.
> The link to the computer is asynchronous (a UART): TX, RX and GND only. That is why the slide calls it the simplest connection.

## 2. The protocol by hand: Elif sends 12 (slides 4-9)

![[cmpe453_lecture_05_1_lecture5_1_p007.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p008.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p009.jpg]]

**Notes.** Elif has a button, Damla sees an LED at the other end of one wire. The pull-up $R_1$ to 5 V keeps the line at 1 while nobody presses. The rules they agree on:
- Button pressed = 0 = LED off. No press = 1 = LED on.
- Send the **LSB first** (bit 0, the rightmost digit).
- Speed: 1 press per second, so one bit lasts 1 s.
- Start bit = 0. Stop bit = 1.

Elif sends 12 = `00001100`. First the start bit 0 (slide 6: Rcvd-bits = `0`). Then the data bits from the right: 0, 0, 1, 1, ... Damla writes each bit down as it arrives: `00`, `000`, `0001`.

The start bit is needed because the line rests at 1: a first data bit 1 would look like "nothing happened". The 1-to-0 change marks the moment to start counting bit times.

> [!info] How to read the circuit on slides 4-15 (beyond the slides)
> - The slides do not draw where the button's left contact goes. It must go to **GND**. Then a press connects the line to 0 V and the line is 0.
> - Button open (drawn as an open switch): only $R_1$ is connected to the line. $R_1$ pulls the line up to 5 V, current flows through $R_1$ and the LED to Gnd, the LED is **on** (filled red dot). This is logic 1.
> - Button pressed (drawn as a closed line): the line is at 0 V, no voltage is left for the LED, the LED is **off** (empty circle). This is logic 0.
> - The red digits in Elif's bubble are the bits already sent. They grow from the right because the LSB goes first. "Rcvd-bits" is Damla's list in the order of arrival, so its first digit is always the start bit.

> [!question]- Check (slides 4-5): Somebody removes the resistor $R_1$ from the circuit. What does Damla see when the button is not pressed, and why does the protocol stop working?
> Without $R_1$ nothing connects the line to 5 V. With the button open the line is not driven at all, so no current flows and the LED is **off**. With the button pressed the line is at 0 V and the LED is off too.
> The LED never changes, so 1 and 0 look the same. The idle level 1 does not exist any more, and the 1-to-0 change of the start bit cannot be seen. $R_1$ (the pull-up) is what makes "no press = 1".

> [!question]- Check (slide 6): Slide 6 shows `Rcvd-bits = 0`. Is this 0 a bit of the number 12? Suppose Elif forgets the start bit and sends only the 8 data bits of 12 and then leaves the line idle. Which byte does Damla decode?
> No. The first 0 is the **start bit**. It carries no data.
> Without a start bit the line shows the data bits of 12, LSB first: `0 0 1 1 0 0 0 0`, then idle `1 1 ...`.
> Damla takes the first 0 as the start bit. Her data bits d0..d7 are the next eight line bits: `0 1 1 0 0 0 0` (seven bits of Elif) and then one idle `1`. The next idle `1` looks like a stop bit.
> d7..d0 = `1000 0110` = `0x86` = **134**, not 12. Every bit is shifted by one place.

> [!question]- Check (slides 7-8): On slides 6 to 8 the LED is off the whole time, for three bits in a row. How does Damla know that this is three bits and not one long bit? On a real line at 2400 baud the level stays low for 1.25 ms. How many bits is that?
> Only by **time**. Both agreed on the bit time (1 s), so 3 s of "off" means three bits: start, d0, d1. The line itself shows no border between equal bits.
> At 2400 baud one bit lasts $1/2400\ \text{s}=416.7$ µs. Number of bits: $1.25\ \text{ms}\times 2400\ \text{bits/s}=3$ bits.

> [!question]- Check (slide 9): After slide 9 Damla has `Rcvd-bits = 0001`. Which bit of the byte is the 1, and what is it worth? What would Damla have after the same four steps if Elif sent 10 = `0x0A` instead?
> The four received bits are start, d0, d1, d2. The 1 is **d2**, worth $2^2=4$. (12 = 8 + 4, the 8 comes next as d3.)
> 10 = `0000 1010`: d0 = 0, d1 = 1, d2 = 0. With the start bit: `Rcvd-bits = 0010`.

## 3. The rest of the frame and decoding (slides 10-15)
![[cmpe453_lecture_05_1_lecture5_1_p010.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p011.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p012.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p013.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p014.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p015.jpg]]

**Notes.** After the last data bit Elif sends the stop bit 1. Damla has received `0001100001`:

| Start | d0 | d1 | d2 | d3 | d4 | d5 | d6 | d7 | Stop |
|---|---|---|---|---|---|---|---|---|---|
| 0 | 0 | 0 | 1 | 1 | 0 | 0 | 0 | 0 | 1 |

Decode: flip the order (`1000011000`), drop stop and start, the data bits are `00001100` = 12.

A **frame** is what goes on the line for one byte. With **8** data bits, **N**o parity and **1** stop bit it is called **8N1**: $1+8+1=10$ bits per byte.

The **baud rate** is the number of bits per second on the line. One bit lasts 1/baud. Elif: 1 baud. The Uno usually uses 9600 baud: $1/9600\ \text{s}=104.2$ µs per bit.

**Asynchronous** means no clock wire. It works because both sides agreed on the bit time in advance and the start bit says when to start counting. If baud rate or frame format differ, the receiver samples the wrong bits and shows garbage.

Bit $i$ of a byte in C: `(data >> i) & 1`.

> [!warning] Watch out
> - The slide's "flip" **reverses the order** (`0001` → `1000`). C's `~` inverts every bit. Decoding a frame never inverts.
> - Baud counts bits, not bytes. At 8N1 one byte costs 10 bits, so 9600 baud carries 960 bytes/s, not 1200.

> [!info] Where the receiver samples, and what a wrong baud rate does (beyond the slides)
> - The receiver waits for the 1-to-0 edge of the start bit. From this edge it counts its **own** bit times.
> - It reads every bit in the **middle**: the start bit at 0.5 bit times after the edge, d0 at 1.5, d1 at 2.5, ..., d7 at 8.5, the stop bit at 9.5.
> - A small clock difference only moves the sample point a little away from the middle, so the bit is still read correctly.
> - A big difference breaks this. If the receiver runs at twice the sender's baud rate, its bit time is half as long and it reads **every line bit twice**. If it runs at half the baud rate, it skips every second bit.
> - If the receiver reads 0 at the place of the stop bit, the frame is invalid. This is called a **framing error**.

> [!question]- Check (slide 10): On slides 9 and 10 the LED is on, exactly as on an idle line. How does Damla know that these are data bits and not "nothing is happening"? At 1 bit per second, with the start edge at $t=0$, during which time is d3 on the line and when should she look?
> She has seen the start bit and is counting. From the start edge on, the next 9 bit times belong to the frame, whatever the level is. Idle begins only after the stop bit.
> The start bit fills 0 s to 1 s. Bit d$i$ fills $(i+1)$ s to $(i+2)$ s. So d3 is on the line from **4 s to 5 s**. She should look in the middle, at about **4.5 s**.

> [!question]- Check (slides 11-12): Slide 11 sends d4 and slide 12 sends d5. A program gets these bits with `(data >> i) & 1`. Compute both for `data = 0x94` and say what the LED does in each of the two steps.
> `0x94` = `1001 0100`.
> d4: `0x94 >> 4` = `0000 1001`, `& 1` gives **1**. Line 1, LED **on**.
> d5: `0x94 >> 5` = `0000 0100`, `& 1` gives **0**. Line 0, LED **off**.
> (For 12 both bits are 0, so the LED is off on both slides.)

> [!question]- Check (slides 13-14): The bits d4 to d7 of 12 are all 0. To save time, Elif stops after d3 and sends the stop bit right away. Damla still expects 8 data bits. Which byte does she decode?
> Line: start `0`, then d0..d3 = `0 0 1 1`, then the stop bit `1`, then idle `1 1 1 ...`.
> Damla reads the stop bit and the idle line as d4..d7 = `1 1 1 1`, and the next idle `1` as her stop bit.
> d7..d0 = `1111 1100` = `0xFC` = **252**, not 12.
> The number of data bits is part of the agreed frame format. Leading zeros must be sent too.

> [!question]- Check (slide 15, decoding): Damla records the 10 bits `0110010110` (first bit first). Decode them the way slide 15 does. Is this a valid 8N1 frame?
> First bit 0: the start bit is correct.
> Last bit **0**: the stop bit must be 1. The frame is **not valid** (framing error).
> The 8 bits in the middle are `11001011`, reversed `1101 0011` = `0xD3`, but this byte cannot be trusted. Probably the baud rate or the frame format is wrong, or the receiver started in the middle of a byte.

> [!question]- Check (slide 15, timing): A link runs at 57600 baud, 8N1. Compute the bit time, the frame time, the number of frames per second, and the time to send 1024 bytes without pauses.
> Bit time: $1/57600\ \text{s}=17.36$ µs.
> Frame time: 10 bits, $10/57600\ \text{s}=173.6$ µs.
> Frames per second: $57600/10=5760$.
> 1024 bytes: $1024\times 10=10240$ bits, $10240/57600\ \text{s}=0.178$ s.

> [!question]- Check (slide 15, baud mismatch): The sender transmits `0x3A` at 4800 baud, 8N1. The receiver is set to 9600 baud, 8N1. Which byte does the receiver decode first? Use the info box above.
> Assumptions: the line is idle (1) before and after this one byte, the receiver starts at the 1-to-0 edge of the start bit and reads in the middle of its own bit times, and after its stop bit it waits for the next 1-to-0 edge.
> Sender bit time $1/4800\ \text{s}=208.3$ µs, receiver bit time $1/9600\ \text{s}=104.2$ µs. The receiver reads every line bit twice.
> `0x3A` = `0011 1010`. Line bits: start `0`, d0..d7 = `0 1 0 1 1 1 0 0`, stop `1`.
> Doubled, as the receiver sees them: `00 00 11 00 11 11 11 00 00 11`.
> Receiver frame = the first 10 of these: start `0`, data d0..d7 = `0 0 0 1 1 0 0 1`, stop `1` (valid by luck).
> d7..d0 = `1001 1000` = **`0x98`**, not `0x3A`.
> The rest of the sender's frame is still on the line: `11 11 00 00 11`, then idle `1 1 ...`. The receiver waits for the next 1-to-0 edge: start `0`, data d0..d7 = `0 0 0 1 1 1 1 1` (three more 0s, the doubled stop bit, three idle 1s), stop = idle `1`. d7..d0 = `1111 1000` = `0xF8`. One sent byte becomes two garbage bytes.

## 4. The USART in the ATmega328P and on the Uno (slides 16-18)
![[cmpe453_lecture_05_1_lecture5_1_p016.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p017.jpg]]
![[cmpe453_lecture_05_1_lecture5_1_p018.jpg]]

**Notes.** Slide 16 is the USART block diagram from the datasheet. Three parts:
- **Clock generator**: the baud rate generator divides the clock by a number from `UBRR0`. This sets the bit time.
- **Transmitter**: `UDR0` (transmit) and the transmit shift register, output on TxD.
- **Receiver**: the receive shift register and `UDR0` (receive), input on RxD.
- Control and status registers: `UCSR0A`, `UCSR0B`, `UCSR0C`.

The USART can run synchronously (with a clock on the XCK pin) or asynchronously. Asynchronous mode is a UART, and that is what the course uses.

Wiring (slide 18): computer → USB → USB/serial adapter → AVR chip.
- RxD = **PD0** (Uno D0, chip pin 2). TxD = **PD1** (Uno D1, chip pin 3).
- TX of one side goes to RX of the other. The wires **cross**.
- Both sides share **GND**.
- The TX and RX LEDs on the Uno blink while data flows.

On the PC the Uno is a serial port (`/dev/ttyUSB0` or `/dev/ttyACM0`). Open a terminal at the program's baud rate, 8N1. Opening the port resets the Uno. Close the terminal before flashing.

> [!warning] Watch out
> - `UDR0` is one name for two buffers. Writing `UDR0 = x;` fills the transmit buffer. Reading `x = UDR0;` gives the last received byte, not what you wrote.
> - Keep D0 and D1 free in UART programs. The USB adapter also uses them for flashing.
> - "Pin 2" and "Pin 3" on slide 18 are legs of the chip, not the Uno's D2 and D3.
> - Slide 18 writes "dublex" for duplex.
> - Garbage characters almost always mean a baud-rate or `F_CPU` mismatch.

> [!info] The parity boxes on slide 16 (beyond the slides)
> - The block diagram has a "Parity Generator" in the transmitter and a "Parity Checker" in the receiver. The lecture uses no parity (8N1), so the slides do not explain them.
> - A **parity bit** is one extra bit for error detection. It is sent **after d7 and before the stop bit**.
> - **Even parity (E)**: the parity bit is chosen so that the number of 1s in the data bits plus the parity bit is even. **Odd parity (O)**: the same count must be odd.
> - Rule: count the 1s in the 8 data bits. Even parity bit = 1 if the count is odd, else 0. The odd parity bit is the opposite.
> - The frame 8E1 or 8O1 has $1+8+1+1=11$ bits per byte.
> - The receiver computes the parity again. If it does not match, one bit (or 3, 5, 7 bits) changed on the way. Two changed bits cancel and are not detected.

> [!info] Voltage levels on the Uno's UART pins (beyond the slides)
> - On D0 and D1 a 1 is about 5 V and a 0 is about 0 V (TTL levels). The idle line is 1, so an idle TX pin sits at about 5 V.
> - The old RS-232 port of a PC uses other voltages: a 1 is a negative voltage and a 0 is a positive voltage, up to about 15 V in size. Never connect it directly to the AVR pins. The USB/serial adapter on slide 18 already gives the right levels.

> [!question]- Check (slide 16, data path): Follow one byte through the block diagram, from the program's `UDR0 = x;` to the TxD pin. Which box turns the 8 parallel bits into a serial stream, and which box decides how long each bit stays on the pin?
> Data bus → **UDRn (Transmit)** → **Transmit Shift Register** → (parity bit added if enabled) → Pin Control → **TxDn**.
> The data bus delivers all 8 bits at once (parallel). The **Transmit Shift Register** shifts them out one by one, LSB first, with start and stop bit around them. It is the parallel-to-serial converter.
> The **Baud Rate Generator** in the clock generator sets the bit time. It divides the clock by a number taken from `UBRRn`.

> [!question]- Check (slide 16, parity): The byte `0x6B` is sent with even parity (8E1) at 19200 baud. Give the parity bit, the complete line bits, and the number of frames per second. What would the parity bit be with odd parity?
> `0x6B` = `0110 1011`. Number of 1s: 5 (odd).
> Even parity: the total must be even, so the parity bit is **1** (5 + 1 = 6).
> LSB first: d0..d7 = `1 1 0 1 0 1 1 0`. Line: start `0`, data `11010110`, parity `1`, stop `1` → **`0 11010110 1 1`** (11 bits).
> Frames per second: $19200/11=1745.45$, so 1745 whole frames. (Bit time $1/19200\ \text{s}=52.08$ µs, frame time $11\times 52.08\ \text{µs}=572.9$ µs.)
> Odd parity: the total must be odd, 5 is already odd, so the parity bit is **0**.

> [!question]- Check (slide 17): A program on the Uno only sends text to the PC and receives nothing. Which of the two yellow-circled LEDs blinks, and which header pin carries the data? You measure this pin with a voltmeter while the program is silent. About which voltage do you read?
> The **TX** LED blinks (the Uno transmits). The data leaves on **TXD = D1** (PD1), the pin labelled `TXD►1` in the yellow box "USART Pins" (the left one of the two pins).
> A silent line is idle, and idle is logic 1. The meter shows about **5 V**.
> The RX LED and D0 would be active only when the PC sends something to the Uno.

> [!question]- Check (slide 18): A temperature logger only sends values from the AVR to the computer. The computer never answers. Which wires of the diagram on slide 18 are the minimum, and is this link simplex, half duplex or full duplex? How many bytes per second can go each way at 9600 baud, 8N1, if both wires are used?
> Minimum: the wire from **TX (PD1) of the AVR to RX of the adapter**, and **GND**. The wire into the AVR's RX (PD0) is not needed.
> Data goes in one direction only, so this is **simplex**.
> With both crossed wires the link is full duplex. Each direction has its own wire, so each carries $9600/10=960$ bytes/s at the same time.

## Key formulas and terms
| Term | Meaning / formula |
|---|---|
| Frame 8N1 | idle 1, start bit 0, 8 data bits LSB first, stop bit 1: 10 bits per byte |
| Decode | drop start and stop, reverse the 8 data bits, convert |
| Baud | line bits per second, bit time = 1/baud (9600: 104.2 µs, 960 bytes/s) |
| Asynchronous | no clock wire, both sides agree on baud and frame |
| Simplex / half / full duplex | one direction / both but one at a time / both at once |
| Bit $i$ in C | `(data >> i) & 1` |
| Hardware | `UBRR0` sets the bit time, `UDR0` write = send, read = received byte, `UCSR0A/B/C` control |
| Pins | RxD = PD0 (D0), TxD = PD1 (D1), cross TX and RX, common GND |

## Check yourself
> [!question]- 1. Write the 8N1 line bits for the number 5.
> 5 = `0000 0101`. LSB first: `10100000`. With start and stop: **`0 10100000 1`**.

> [!question]- 2. A receiver records the frame `0110100101` (first bit first). Which byte and character was sent?
> Drop start and stop: `11010010`. Reverse: `0100 1011` = **`0x4B`** = 75 = `'K'`.

> [!question]- 3. Elif sends the byte 200 at 1 bit per second. How long does it take, and what does Damla write down?
> 10 bits × 1 s = **10 s**. 200 = `1100 1000`, LSB first `00010011`, with start and stop **`0000100111`**.

> [!question]- 4. Why is a start bit needed, and why must it be 0? Why is there a stop bit 1?
> The line rests at 1, so only a 0 is a change the receiver is sure to see. It marks when to start counting. The stop bit returns the line to 1, so the next start bit is again a visible 1-to-0 change.

> [!question]- 5. A loop prints "Hello\r\n" (7 characters) at 9600 baud, 8N1. How long is one line and how many lines per second fit?
> $7\times10=70$ bits. $70/9600\ \text{s}=$ **7.29 ms**. $960/7=137.1$, so **137** whole lines per second.

> [!question]- 6. A student wires TX to TX and RX to RX between two Unos. What happens?
> Both transmitters drive the same wire and both receivers listen to a wire nobody drives. No byte arrives. TX must meet RX, plus GND to GND.
