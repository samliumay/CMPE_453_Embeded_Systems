# CMPE 453 · Lecture 2.1 · Programming the AVR: the toolchain

> [!summary] In short
> - Toolchain: editor writes C, compiler makes machine code (`.hex`), flash programmer copies it into the AVR's flash. The Arduino IDE does all three.
> - A HEX record is `:LL AAAA TT data CC`. Checksum $CC=(256-(\text{sum}\bmod 256))\bmod 256$.
> - HEX files count **bytes**, the CPU counts 16-bit **words**: word address = byte address / 2. The AVR is little endian (low byte first).
> - Data bus and ALU are 8 bit, the program bus is 16 bit. That is why the AVR is "8-bit".
> - Pin map: D0-D7 = PD0-PD7, D8-D13 = PB0-PB5, A0-A5 = PC0-PC5.
> - Blinker: `DDRB |= 0b00000001;` makes PB0 an output. `|=` sets the mask bits and keeps the rest, `=` overwrites all eight.

## 1. The toolchain and why C (slides 2-3)
![[cmpe453_lecture_02_1_lecture2_1_p002.jpg]]
![[cmpe453_lecture_02_1_lecture2_1_p003.jpg]]

**Notes.** The AVR cannot read C. The chain is: ideas → (editor) → C code → (compiler) → machine code, the `.hex` file → (flash programmer) → AVR flash.

| Step | Arduino IDE | Command line |
|---|---|---|
| Editor | the IDE window | any editor |
| Compiler | "Verify" button | `avr-gcc`, then `avr-objcopy` makes the `.hex` |
| Flash programmer | "Upload" button | `avrdude` talks to the Uno's bootloader |

Why C and not assembly (slide 3): easier and faster to write, easier to modify, good libraries, portable. The compiler still makes tight code: `DDRB |= 0b00000001;` becomes the single instruction `sbi 0x04, 0` (set bit 0 of I/O register 0x04, which is `DDRB`).

> [!warning] Watch out
> The compiler only makes a file on the laptop. Nothing reaches the chip until the flash programmer copies it. "Done compiling" with no board connected is normal.

> [!question]- Check (slide 2): Put the three tools `avrdude`, `avr-gcc` and a text editor on the arrows of the slide's diagram. Which arrow is the only one that needs the board to be connected?
> Ideas → C code is the **editor**. C code → machine code is the compiler, **`avr-gcc`** (with `avr-objcopy` for the `.hex`). Machine code → AVR is the flash programmer, **`avrdude`**.
> Only the last arrow needs the board. The editor and the compiler only make files on the laptop.
> The slide names only the Arduino IDE. The three command-line tool names are beyond the slides.

> [!question]- Check (slide 3): The compiler produced `sbi 0x05, 3`. I/O register 0x05 is `PORTB`. What does the instruction do, and which C line gives it? Which reason on the slide does this show?
> `sbi` means "set bit in I/O register" (beyond the slides). So it sets bit 3 of register 0x05: `PORTB` bit 3 becomes 1. If PB3 is an output, the pin goes to 5 V.
> In C: `PORTB |= 0b00001000;`.
> Reason: C is easier to write and to change. You write the name `PORTB`, not the number 0x05, and you do not have to know the instruction `sbi`.

## 2. Inside a HEX file (slide 4)
![[cmpe453_lecture_02_1_lecture2_1_p004.jpg]]

**Notes.** Each line (record) says "put these bytes at this address". Two hex characters are one byte.

$$\texttt{:}\ \underbrace{\texttt{LL}}_{\text{byte count}}\ \underbrace{\texttt{AAAA}}_{\text{address}}\ \underbrace{\texttt{TT}}_{\text{type}}\ \underbrace{\texttt{DD}\cdots\texttt{DD}}_{\text{LL data bytes}}\ \underbrace{\texttt{CC}}_{\text{checksum}}$$

Type `00` is data, type `01` (the line `:00000001FF`) is end of file.

> [!example] Decode `:107E000011E0A0E0B1E0E0E1F0E802C005900D92E1`
> - Pairs: `10 | 7E 00 | 00 | 11 E0 A0 E0 B1 E0 E0 E1 F0 E8 02 C0 05 90 0D 92 | E1`.
> - Byte count 0x10 = 16. Address 0x7E00. Type 00 (data). Checksum 0xE1.
> - Data: 0x7E00 = 0x11, 0x7E01 = 0xE0, ..., 0x7E0F = 0x92.
> - Checksum: header $16+126+0+0=142$. Data in fours: $625+850+666+308$. Total $2591$. Low byte: $2591-10\cdot256=31$. $256-31=225=$ 0xE1. Correct.

**Checksum rule.** Add all bytes from the byte count to the last data byte. Keep the low 8 bits. The checksum is 256 minus that. Check: the sum of all bytes including CC ends in `00`.

**Byte and word addresses.** The ATmega328P has 32 KB flash = 32768 bytes = 16384 words.
- Byte addresses (HEX file, `avr-objdump`): 0x0000-0x7FFF.
- Word addresses (program counter): 0x0000-0x3FFF.
- 0x7E00 / 2 = 0x3F00 (in binary: shift one place right).

Little endian: bytes `11 E0` form the word 0xE011 (word 0x3F00), bytes `A0 E0` form 0xE0A0 (word 0x3F01). 0xE011 is `ldi r17, 0x01`.

> [!warning] Slide bug
> The slide writes "Atmega328p: address range 0x0000-0x3FFF" right after the byte address 0x7E00. That range is in **words**. In bytes the flash is 0x0000-0x7FFF, so 0x7E00 is a valid byte address.
> Also: the three pictures on slide 4 come from different files. They show what each tool's output looks like, they do not decode each other.

> [!info] Why 0x7E00
> On the Uno the top 512 bytes of flash, 0x7E00-0x7FFF, hold the bootloader. That is why the IDE says "Maximum is 32256 bytes": $32768-512=32256=$ 0x7E00.

> [!info] How to read an `avr-objdump` line (beyond the slides)
> The picture at the bottom left of slide 4 is the output of `avr-objdump -d` ("show the machine code as assembly"). Each line has three parts, for example `1ca:  cf 92   push r12`:
> - `1ca:` is the **byte address** in flash, in hex. It goes up by 2 per line, because one instruction is 2 bytes (one 16-bit word).
> - `cf 92` are the two bytes in the order they are stored. Low byte first (little endian), so the instruction word is 0x92CF.
> - `push r12` is the same instruction written in assembly.
>
> The slide's rule "3F00 = 0xE011" is the same idea: take two stored bytes, swap them to get the word, and divide the byte address by 2 to get the word address.

> [!question]- Check (slide 4, record): A record starts with `:10006000`. At which byte address does its last data byte go? At which address must the next full record start?
> Byte count `10` is 0x10 = 16 bytes. Address `0060` is 0x0060. Type `00` is data.
> The 16 bytes fill 0x0060 to $\text{0x0060}+16-1=\text{0x0060}+\text{0x0F}=$ **0x006F**.
> The next record starts one byte later, at $\text{0x0060}+\text{0x10}=$ **0x0070**. This is why the addresses in the slide's listing go up in steps of 0x10: 0x0000, 0x0010, 0x0020, ...

> [!question]- Check (slide 4, avr-objdump): The listing on the slide has the line `1d0:  ff 92  push r15`. What is the 16-bit instruction word, and what is its word address?
> Little endian: the first stored byte `ff` is the low byte, the second `92` is the high byte. Word = **0x92FF**.
> Byte address 0x01D0 = $1\cdot256+13\cdot16+0=464$. Word address = $464/2=232=$ **0x00E8**.

## 3. Recall: inside the AVR (slide 5)
![[cmpe453_lecture_02_1_lecture2_1_p005.jpg]]

**Notes.** The CPU fetches 16-bit instructions from program ROM (flash) on one bus. It moves 8-bit data to and from RAM, EEPROM, timers and ports on a second bus.

- Data bus: **8 bits**. Program bus: **16 bits**. ALU: **8-bit** data.

"8-bit" names the data width, not the instruction width.

| Block | Job | ATmega328P |
|---|---|---|
| Program ROM (flash) | holds the program, kept without power | 32 KB |
| RAM | variables, lost at power-off | 2 KB SRAM |
| EEPROM | data the program saves, kept without power | 1 KB |
| Timers | count clock ticks: delays, PWM | 3 timers |
| Ports | the I/O pins | B, C, D |
| OSC | the clock | 16 MHz on the Uno |

The architecture overview is in [[CMPE453 L00 - Course intro and lab kit]], part B.

> [!question]- Check (slide 5): Use the block diagram. (a) Where is the uploaded Blinker program stored, and on which bus does it reach the CPU? (b) Where does a variable `count` live, and on which bus does it travel? (c) Which of the two is still there after power-off?
> (a) In the program ROM (flash). The CPU fetches it over the program bus, 16 bits wide, one instruction word at a time.
> (b) In RAM. It moves over the data bus, 8 bits wide, the same bus that connects EEPROM, timers and ports.
> (c) The program. Flash keeps its content without power, RAM loses it.

## 5. Blinker: circuit and pin mapping (slides 11-13)
![[cmpe453_lecture_02_1_lecture2_1_p011.jpg]]
![[cmpe453_lecture_02_1_lecture2_1_p012.jpg]]
![[cmpe453_lecture_02_1_lecture2_1_p013.jpg]]

**Notes.** Circuit: Arduino digital pin 8 → resistor → LED → GND. With a 330 Ω resistor and a red LED (about 2.2 V): $I=(5-2.2)/330\approx 8.5$ mA, safe for a pin.

The board prints Arduino numbers. The C code uses AVR names. Always translate first.

| Arduino pins | AVR pins | Register bits |
|---|---|---|
| D0-D7 | PD0-PD7 | Port D, bits 0-7 |
| D8-D13 | PB0-PB5 | Port B, bits 0-5 (bit = D-number − 8) |
| A0-A5 | PC0-PC5 | Port C, bits 0-5 |

Example: D2 = PD2, D10 = PB2, A3 = PC3. Lab 1 pins 7, 9, 12 are PD7, PB1, PB4. The on-board LED "L" is D13 = PB5.

> [!question]- Check (slide 12): The circuit is rebuilt with a 220 Ω resistor and a green LED that drops about 2.0 V. Compute the current. Is it inside the "recommended 20 mA" per pin printed on the pinout diagram of slide 13?
> Voltage across the resistor: $5-2.0=3.0$ V.
> Ohm's law: $I=V/R=3.0/220=0.0136$ A $\approx 13.6$ mA.
> $13.6<20$, so it is inside the recommended value (and far below the absolute maximum of 40 mA per pin on the same diagram).

> [!question]- Check (slide 13): LEDs are on Arduino D4 and D6, and one more on A5. Give the AVR pin names. Then write one line that makes D4 and D6 outputs and keeps the other pins of that port as they are.
> D4 and D6 are in D0-D7, so port D with the same bit number: **PD4** and **PD6**. A5 is **PC5**.
> Mask with bits 6 and 4 set: `0b01010000`. Direction register of port D is `DDRD`:
> `DDRD |= 0b01010000;`
> `|=` keeps the other six bits of `DDRD`.

## 6. Blinker: the code and `|=` (slides 14-18)
![[cmpe453_lecture_02_1_lecture2_1_p014.jpg]]
![[cmpe453_lecture_02_1_lecture2_1_p015.jpg]]
![[cmpe453_lecture_02_1_lecture2_1_p016.jpg]]
![[cmpe453_lecture_02_1_lecture2_1_p017.jpg]]
![[cmpe453_lecture_02_1_lecture2_1_p018.jpg]]

**Notes.** Open the IDE, delete the empty sketch, paste the code. Slide 16 (Include Library) is not needed here.

```c
#include <avr/io.h>        /* Defines pins, ports, etc */
#include <util/delay.h>    /* Functions to waste time */
int main(void) {
  DDRB |= 0b00000001;      /* 1 is OUTPUT, 0 is INPUT */
  while (1) {
    PORTB = 0b00000001;    /* Turn on only pin 0 of PORTB */
    _delay_ms(1000);
    PORTB = 0b00000000;    /* Turn off all pins on PORTB */
    _delay_ms(1000);
  }
  return 0;                /* never reached */
}
```

| Register | Job (bit $n$ is pin Pxn) |
|---|---|
| `DDRB` | direction: 1 = output, 0 = input |
| `PORTB` | output value: 1 = 5 V, 0 = 0 V |
| `PINB` | read the pins |

Trace: `DDRB` goes `0b00000000` → `0b00000001`. In the loop `PORTB` is `0b00000001` for 1 s (LED on), then `0b00000000` for 1 s (LED off). One blink every 2 s = 0.5 Hz. `_delay_ms` needs `F_CPU` (16 MHz on the Uno).

**Why `|=` and not `=`.** `REG |= MASK;` means `REG = REG | MASK;`. Mask bits that are 1 become 1, the others keep their value ($x\,|\,0=x$, $x\,|\,1=1$).

> [!example] `DDRB` is `0b00100000` (PB5 already an output)
> - `DDRB |= 0b00000001;` gives `0b00100001`: PB0 and PB5 are outputs.
> - `DDRB = 0b00000001;` gives `0b00000001`: PB5 silently became an input again.

> [!warning] Watch out
> `|=` can only turn bits on. To turn a bit off use `&=` with a 0 in the mask: `PORTB &= 0b11111110;`. The loop's `PORTB = ...` overwrites all of port B. That is fine here only because nothing else is on port B.

> [!info] Reading the code word by word (beyond the slides)
> - `#include <avr/io.h>` runs nothing. It only gives the names `DDRB`, `PORTB`, ... to the compiler. `#include <util/delay.h>` gives the function `_delay_ms()`.
> - `0b` means "a binary number follows". The rightmost digit is bit 0, the leftmost is bit 7. So `0b00000001` has only bit 0 set, and bit 0 of port B is PB0 = D8.
> - `=` stores a value. `==` would compare.
> - `while (1)`: 1 is always true, so the body repeats forever. An embedded program never ends, there is nothing to return to. That is why `return 0;` is never reached.
> - At reset `DDRB` and `PORTB` are both `0b00000000`: all pins are inputs.
> - Compared with the empty sketch on slide 15: the lines before `while (1)` do the job of `setup()` (run once), the body of `while (1)` does the job of `loop()` (run again and again).

> [!question]- Check (slide 15): The empty sketch on the slide has `setup()` and `loop()`. The course deletes both and writes `main()`. Which lines of the Blinker's `main()` do the job of `setup()`, and which do the job of `loop()`?
> `setup()` runs once: this is the part before `while (1)`, here `DDRB |= 0b00000001;`.
> `loop()` runs again and again: this is the body of `while (1)`, the two `PORTB = ...` lines and the two `_delay_ms(1000);` lines.

> [!question]- Check (slide 16): The slide shows *Sketch → Include Library → AVR-Programming-Library* and says the step is not needed here. Why does the Blinker compile without it?
> The Blinker uses only `DDRB`, `PORTB` and `_delay_ms()`. These come from `avr/io.h` and `util/delay.h`, which are part of every `avr-gcc` installation. Nothing in the code comes from Williams' library, so there is nothing to include from it.

> [!question]- Check (slides 17-18, change the blink): Change the Blinker so that the on-board LED (D13) is on for 200 ms and off for 800 ms. Which values change? What is the blink frequency?
> D13 = PB5, so the mask is `0b00100000` instead of `0b00000001`.
> - `DDRB |= 0b00100000;`
> - `PORTB = 0b00100000;` then `_delay_ms(200);`
> - `PORTB = 0b00000000;` then `_delay_ms(800);`
>
> One period is $200+800=1000$ ms $=1$ s. Frequency $=1/1\text{ s}=1$ Hz. The LED is on for $200/1000=20\%$ of the time.

> [!question]- Check (slides 17-18, find the bug): A student rewrites the loop with the OR-assign operator in both lines "to be safe". The LED turns on and never turns off. Why?
> ```c
> while (1) {
>   PORTB |= 0b00000001;
>   _delay_ms(1000);
>   PORTB |= 0b00000000;
>   _delay_ms(1000);
> }
> ```
> `PORTB |= 0b00000000;` is `PORTB = PORTB | 0b00000000;`. OR with 0 keeps every bit ($x\,|\,0=x$), so bit 0 stays 1.
> `|=` can only turn bits on. To turn only PB0 off, use `PORTB &= 0b11111110;`.

## Key formulas and terms
| Term | Meaning / formula |
|---|---|
| Toolchain | editor → C → compiler → `.hex` → flash programmer → AVR |
| HEX record | `:LL AAAA TT data CC`, type 00 data, 01 end of file |
| Checksum | $CC=(256-(\text{sum}\bmod 256))\bmod 256$ |
| Addresses | bytes 0x0000-0x7FFF = words 0x0000-0x3FFF, word = byte / 2 |
| Little endian | low byte stored first: `11 E0` is the word 0xE011 |
| AVR buses | data bus 8 bit, program bus 16 bit, ALU 8 bit |
| Pin map | D0-D7 = PD0-PD7, D8-D13 = PB0-PB5, A0-A5 = PC0-PC5 |
| `REG \|= MASK` | sets the mask bits, keeps the rest |
| `sbi 0x04, 0` | set bit 0 of `DDRB` (0x04). `PORTB` is 0x05 |
| `.elf` vs `.hex` | `.elf` has symbols (for `avr-size`, `avr-objdump`), `.hex` is plain records (for `avrdude`) |

## Check yourself
> [!question]- 1. Decode `:0200B000FFCF80` and check the checksum.
> `02 | 00 B0 | 00 | FF CF | 80`: 2 bytes at 0x00B0, type 00, data `FF CF`. Sum $2+0+176+0+255+207=640$. $640-2\cdot256=128$. $256-128=128=$ **0x80**, correct. The word is 0xCFFF = `rjmp .-2`, an endless loop.

> [!question]- 2. Compute the missing checksum of `:040100000C943E00??`.
> Sum $4+1+0+0+12+148+62+0=227$. $256-227=29=$ **0x1D**.

> [!question]- 3. An instruction sits at byte address 0x01CA. What is its word address? Which bytes store the word 0x940C?
> $\text{0x01CA}=458$, $458/2=229=$ **0x00E5**. Little endian: stored as `0C 94`.

> [!question]- 4. Why is the AVR called 8-bit if its instruction bus is 16 bits wide?
> "8-bit" names the data width: the data bus and the ALU handle 8 bits at a time. Instructions travel on the separate 16-bit program bus.

> [!question]- 5. An LED is on Arduino D11 and another on A0. Give port and bit.
> D11: port B, bit $11-8=3$, **PB3**. A0: **PC0**.

> [!question]- 6. `DDRB` is `0b00011000`. Value after `DDRB |= 0b00000001;` and after `DDRB = 0b00000001;`?
> `|=`: **`0b00011001`** (PB4, PB3 stay outputs, PB0 added). `=`: **`0b00000001`** (PB4 and PB3 become inputs). The Blinker should use `|=`.
